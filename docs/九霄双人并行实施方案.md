## 1. 结论先行

《九霄》的长期目标仍是七个阶段。上一版把交付准备压缩成了 0—5 阶段，造成命名混乱。本版恢复最初的七阶段：

1. 基础游戏；
2. 理解玩家；
3. 权威世界状态；
4. 长期记忆与世界历史；
5. NPC 独立认知；
6. 动态开放世界；
7. 核心能力平台化。

多端上架、后端和商业化不应列成第八阶段。它们是三条横切轨道，贯穿七阶段：

- **游戏轨道**：玩法、规则、状态、记忆、NPC 和世界演化；
- **平台轨道**：响应式 Web/PWA、Android、iOS、HarmonyOS NEXT、桌面与 Steam；
- **商业轨道**：账号、云存档、权益、支付、模型成本、隐私和内容合规。

当前优先级没有改变：先使 0 号试玩稳定可玩，再建立真正的规则垂直切片。此时直接开发“通用开放大世界平台”会把尚未验证的错误接口固化。

## 2. 两个人的权威边界

### 2.1 合作者

合作者是项目发起者、产品主理人和 Canon 负责人。他主导：

- 项目宗旨与核心体验；
- 修仙世界设定与冲突裁决；
- 人物、剧情、叙事节奏与审美方向；
- 玩法场景和产品验收；
- 哪些改变仍然属于《九霄》。

他不应被降格为“提需求的人”。但产品裁决也必须写成可验收规格。口头愿景不能直接进入实现。

### 2.2 你

你是技术联合负责人、AI/Agent 架构负责人和工程交付负责人。你主导：

- 行动中间表示、规则引擎、状态与事件契约；
- AI、Jev、Mem0、检索和记忆实验；
- Web、原生外壳、后端与商业技术路线；
- 存档迁移、隐私、安全、测试、CI 与发布；
- 对新技术方案做基准测试，阻止“因流行而采用”。

你不应替合作者擅自决定世界观。合作者也不应绕过契约，让模型直接改写权威状态。

### 2.3 双钥匙发布

任何正式 Release 同时需要两把钥匙：

- **产品钥匙**：合作者确认体验、人物和 Canon 没有偏离；
- **工程钥匙**：你确认数据、隐私、兼容、成本和恢复能力合格。

任意一把未通过，只能标为实验版或试玩候选版。

### 2.4 决策权矩阵

| 事项 | 主导者 | 必须审查者 | 裁决规则 |

## 3. 当前事实与必须纠正的判断

### 3.1 已经存在

- 手机响应式单 HTML；
- 建角、自由行动、行动建议；
- 多存档、导入导出和旧档迁移；
- 单 AI/多 AI 岗位、失败回退和调用日志；
- STM/LTM、世界事件、伏笔和档案建议；
- JSON 兼容解析、状态校验、取消与重试恢复；
- 核心、AI/JSON、浏览器逻辑与移动布局模拟测试。

### 3.2 尚未被证明

- 真实模型数十到数百小时的稳定性；
- AI 已能把自然语言可靠转成规则动作；
- 规则引擎已经成为世界事实来源；
- NPC 已有独立认知与信息传播；
- 世界能在玩家离开时演化；
- 全部 182 张 OCR 已经人工核准；
- iOS、Android、HarmonyOS NEXT、PC 或 Steam 已完成真机/商店验收。

### 3.3 三个常见误判

**“纯 Web 不能商业化”不准确。** Web 可以收费，也可以发行。真正的缺口是账号、权益、服务端密钥、云存档、支付验证、成本控制和合规。若只做一次性买断加 BYOK，后端可以很薄；若出售内置 AI、跨端权益或订阅，后端几乎不可避免。

**“套一个原生壳就能上架”不准确。** Apple 明确要求应用超越简单的网站重新封装。应用还要处理支付、隐私、审核账号、内容安全、文件系统、生命周期与真机交互。

**“有 RAG 就有长期世界记忆”不准确。** RAG 只决定哪些文本被取回。它不能保证人物已死、物品所有权或境界规则永远正确。

## 4. 目标架构：七个职责层

```text
玩家自然语言
    ↓
Intent 层：ActionIntent / ambiguity / required clarification
    ↓
Decision 层：Jev 或通用模型给出分类、候选与置信度
    ↓ 只提交提案
Rule 层：合法性、数值、随机种子、冲突和不变量
    ↓ 只由规则层提交
Event 层：不可变 DomainEvent
    ↓ 投影
State 层：人物、物品、地点、时间、关系、任务、势力
    ↓ 检索与视角过滤
Memory 层：玩家记忆、NPC 记忆、摘要、遗忘和世界历史
    ↓ 已结算事实
Narrative 层：小说正文、选项、场景图和声音
```

必须维持单向边界：叙事模型可以改写表达，不能反向改写结算事实。

## 5. Mem0、UwU Memory 与 Jev 的采用结论

### 5.1 Mem0：候选适配器，不是数据库真相

适用范围：

- 人物偏好、经历和关系的语义检索；
- 玩家长期偏好；
- NPC 可回忆事件的候选召回；
- 多跳人物/地点相关检索实验。

不适用范围：

- 物品所有权；
- 死亡、生存与境界；
- 任务状态、货币和地图连通；
- 任何需要强一致性和事务保证的事实。

Mem0 的 Graph Memory 当前主要用实体共现提升检索排序。其官方文档明确说，它不产生带类型的关系边。因此不能把它当作《九霄》的领域知识图谱。

采用方式：定义 `MemoryAdapter`。先做 `LocalMemoryAdapter`，再做 `Mem0Adapter`。两者用同一组记忆评测数据对比。不得让业务代码直接依赖 Mem0 SDK。托管版与开源版的能力、数据位置和版本迁移必须分开评估。未明确玩家数据会传到哪里之前，不得上传私人世界书或 NPC 长期记忆。

### 5.2 UwU Memory：借鉴管线，不整包嵌入产品

可借鉴：

- 保护最近回合；
- 旧消息自动摘要；
- 向量检索与最近记忆保底；
- 摘要可查看、编辑、重建和删除；
- 后端不可用时降级到最近记忆。

不能照搬：

- 它依赖 SillyTavern 扩展与服务端插件结构；
- 摘要仍由模型生成，可能遗漏或改写事实；
- 相似度阈值不是世界规则；
- “无限上下文”是产品措辞，不是可验证的无损保证。

采用方式：复制设计原则和测试场景。若复用 MIT 代码，必须保留许可证与来源，并先做代码审计。更合理的路径是按《九霄》的事件契约重写一个小型摘要/检索适配器。

### 5.3 Jev：判断器，不是修仙规则裁判

Jev 官方定位是把结构化状态和问题转成类型化判断、概率与置信度。它适合：

- 行动类型分类；
- 是否需要追问；
- 从有限合法动作中选择候选；
- 剧情节奏或分支优先级评分；
- 高频、低成本、低延迟路由。

它不应直接决定：

- 雷符是否实际消耗；
- 山洞是否坍塌；
- 角色是否死亡；
- 境界能否突破；
- NPC 是否知道某个秘密。

这些结果必须由领域规则和事件提交。供应商关于“零幻觉”的措辞属于厂商主张，不能替代本项目实测。

Jev 只在阶段二做时间盒实验，并与两条基线比较：

1. 纯确定性规则/关键词分类；
2. 通用模型结构化输出。

比较指标：意图准确率、拒识率、校准误差、P95 延迟、每千次成本、错误升级率和离线可用性。未胜过基线，不进入主链。

## 6. “真实遗忘”应如何实现

真实遗忘是可行的产品差异点，但不能等于删除数据。

### 6.1 四层隔离

| 层 | 内容 | 是否允许遗忘 |
| --- | --- | --- |
| 世界真相 | 事件日志和当前状态 | 不允许 |
| NPC 观察 | NPC 亲眼见、听说或推测的记录 | 不删除，可失去可访问性 |
| NPC 信念 | NPC 当前相信的版本、来源和置信度 | 可衰减、被干扰、被纠正 |
| 叙事回忆 | 该场景下实际取回并表达的内容 | 可遗漏、模糊或混淆 |

一个 NPC 忘记某人死亡，不会使死者复活。它只会让 NPC 的话或行动表现出不知道、记不清或不相信。

### 6.2 两种存档模式

- **经典模式**：重要 NPC 事实默认可检索。适合稳定剧情和普通玩家。
- **拟真记忆模式**：检索可访问性随时间、干扰和提示变化。适合愿意接受误解与遗忘的玩家。

模式写入新档 `memoryPolicyId`。中途切换必须生成迁移预览，不能静默改变所有人物。

### 6.3 原型模型

每条 NPC 记忆至少包含：

```text
eventId, npcId, source, observedAt, valence, salience,
storageStrength, retrievalStrength, lastRecalledAt,
confidence, secrecy, contradictedBy, policyVersion
```

候选召回分数可从以下因素开始：

```text
recallScore = cueMatch × salience × confidence × recencyDecay
              × relationshipWeight × sourceReliability
              − interferencePenalty
```

这只是游戏启发式，不应宣称为人类认知模型。认知研究区分“存储强度”和“提取强度”，也指出许多遗忘属于检索失败而非痕迹永久消失。因此，首版只模拟可访问性，不模拟不可逆删除。

### 6.4 必测场景

- 一个秘密只被 A 看见，B 不应凭空知道；
- A 多年后在弱提示下想不起，在强提示下可能想起；
- 重复回忆提高可访问性，但不能提高事实真实性；
- 谣言传播改变信念，不改变世界真相；
- 相似人物和事件形成干扰；
- 高情绪或高关系事件衰减更慢；
- GM 覆盖必须生成明确事件，不得伪装为记忆恢复。

## 7. 地图、图片剧情与开放世界

开放世界不应从“生成更大的图”开始。首个可验证版本应是节点地图：

```text
Location(id, name, region, tags, stateVersion)
Edge(from, to, travelTime, conditions, visibility)
SceneAsset(locationId, stateVersion, mode, provenance)
```

玩家点击箭头，实际改变的是位置事件。图片只是某个地点状态的投影。地点被毁、季节改变或势力易主时，可换用新的场景资源，但旧图仍保留来源和版本。

叙事支持两种展示模式：

- **小说模式**：以长文本和状态面板为主；
- **图片剧情模式**：短文本、人物立绘、场景图和分镜为主。

两种模式必须共享同一事件与状态，不能形成两个游戏逻辑。图片生成应在阶段六之后评估。首版优先使用审核过的静态或半动态资源，避免生成成本与角色一致性同时失控。

## 8. 七阶段执行路线

时间只是量级估算，不是承诺。每阶段必须满足出口条件后再扩大范围。

### 阶段一：完成基础游戏

**目标**：让 0 号试玩成为可重复游玩的响应式 Web 游戏。

**内容**：建角、修炼、物品、关系、地图节点、时间、任务、基础战斗、剧情、存档、移动端 UI。

**合作者**：产品宪章、关键 Canon、10 个代表场景、叙事与 UI 验收。

**你**：修复构建一致性、真实 API 矩阵、存档稳定、PWA 基线、CI 和发布流程。

**出口**：真实模型 30 回合、关键玩法闭环、目标手机实测、无不可恢复存档损坏。

### 阶段二：让系统理解玩家

**目标**：玩家文本先成为动作提案，不再直接交给剧情模型续写。

**内容**：`ActionIntent`、实体绑定、歧义追问、动作原子、Jev 对照实验。

**合作者**：提供 200 条真实玩家表达、期望动作和歧义案例。

**你**：Schema、解析器、校准评测、失败拒绝和可观察日志。

**出口**：核心动作测试集达到事先约定的准确率；低置信度不推进世界；Jev 是否采用有数据结论。

### 阶段三：建立权威世界状态

**目标**：规则和事件成为事实来源。

**内容**：领域规则、确定性随机种子、事件日志、状态投影、幂等与迁移。

**代表切片**：假装受伤→诱敌入洞→使用雷符→山洞坍塌→伤亡/逃脱。

**合作者**：规则边界、战力语义和结果合理性。

**你**：结算器、事件提交、重放、属性测试和调试面板。

**出口**：同一输入与种子同一结果；1000 次模拟核心不变量零违规；改写叙事不能改事实。

### 阶段四：长期记忆与世界历史

**目标**：长局可检索、可审计、可压缩，但不可被摘要篡改。

**内容**：原始事件、剧情摘要、人物记忆、检索、反思、世界年表、两种遗忘模式。

**合作者**：定义哪些事件应铭记、可模糊或应遗忘，并验收记忆表现。

**你**：`MemoryAdapter`、Local/Mem0 实验、UwU 风格摘要管线、重建和质量评测。

**出口**：事件可重建摘要；召回错误可定位；至少一条长局跨 100 回合无硬事实漂移。

### 阶段五：NPC 独立认知

**目标**：世界真相与人物所知分离。

**内容**：观察、来源、传播、秘密、谣言、欺骗、信念冲突、遗忘和关系影响。

**合作者**：为关键人物定义认知边界、人格化记忆和错误判断。

**你**：知识 ACL、传播事件、置信度更新、视角过滤和泄漏测试。

**出口**：NPC 只获取合法来源；秘密泄漏可追溯；同一事件对不同 NPC 产生不同但可解释的认知。

### 阶段六：动态开放世界

**目标**：玩家不在场时，世界仍按受控规则演化。

**内容**：世界时钟、宗门与经济、NPC 日程、离线演化、冲突结算、节点地图版本和可选图片剧情。

**合作者**：定义“世界活着”的最低体验和大事件边界。

**你**：调度预算、分层模拟、快进、冲突合并、性能和成本上限。

**出口**：离线演化可重放；不会因长时间跨度爆炸；玩家回访能看到可解释变化。

### 阶段七：抽离平台与多系列

**目标**：九霄从完整游戏变成第一款内容包，而不是被重构拖垮。

**内容**：通用动作、规则、记忆、事件、角色卡、世界书、API 和内容包契约。

**第二垂直切片**：建议用恋爱题材验证关系、秘密、日程与记忆，但不得先复制整套九霄代码。

**合作者**：担任九霄内容包负责人，并定义新系列的体验差异。

**你**：插件边界、SDK、迁移、权限、内容审核和工具链。

**出口**：第二题材复用核心而不引入修仙特例；九霄仍可独立迭代；平台契约经历真实版本迁移。

## 9. 多端交付路线

| 时点 | 目标 | 建议技术 | 不能跳过的验收 |
| --- | --- | --- | --- |
| 现在 | Web/PWA | 现有响应式 Web，补 manifest、离线边界和安装体验 | iOS Safari、Android Chrome、存档、键盘、后台恢复 |
| 阶段一后 | Android/iOS 候选 | Capacitor 原生外壳 | 安全存储、文件、网络、生命周期、IAP 沙盒、商店审核 |
| 阶段一后单独评估 | HarmonyOS NEXT | ArkTS/ArkUI 外壳 + ArkWeb + JSProxy | DevEco、签名、文件选择、键盘、支付与真机；不得用 APK 结果替代 |
| 阶段三后 | PC 桌面 | Tauri 2 候选 | WebView2/macOS WebKit 差异、自动更新、存档路径和签名 |
| 阶段三或四后 | Steam | 桌面包 + Steamworks | 商店材料、Steam Direct、云存档/成就可选、审核与控制器/窗口行为 |

Capacitor 官方支持把现有 Web 项目加入 iOS 和 Android。它不等于 HarmonyOS NEXT 支持。HarmonyOS 需要单独使用 ArkWeb/ArkTS 路线并做真机验证。Tauri 能复用 Web 前端构建桌面应用，但仍要接受各平台 WebView 差异。

## 10. 后端与商业化

### 10.1 推荐产品模式

初期采用混合模式：

- 免费或一次性买断的 BYOK 本地模式；
- 未来提供含模型额度、云存档和跨端同步的订阅模式；
- 两种模式共享游戏规则，不形成“付费才能不崩”的差异。

### 10.2 后端最小模块

```text
Auth         匿名/正式账号、设备迁移
Entitlement  购买、订阅与恢复权益
Save Sync    加密云存档、冲突解决、版本迁移
AI Gateway   服务端密钥、限流、配额、厂商路由、成本记录
Receipt      Apple/Google/华为/Steam 回执验证
Safety       内容分级、举报、审计和必要的生成安全策略
Telemetry    明示同意、最小采集、崩溃与性能
```

不应在 0 号试玩前一次做完。先写接口和威胁模型，再按商业方案逐步实现。

### 10.3 费用与审核约束

- Apple 对解锁数字功能通常要求 In-App Purchase，也要求应用超越简单网站封装；
- Google Play 对应用内数字功能与内容通常要求 Play Billing，具体地区例外须按当时政策核对；
- Apple 要求公开并在应用内可访问的隐私政策；
- 使用第三方模型时，玩家的剧情、世界书或角色记忆可能被发送到外部服务。必须明确告知；
- 自带 Key 不能免除内容、隐私和商店责任；
- 订阅必须先做单位经济模型：每活跃用户回合数、输入/输出 token、图片成本、支付抽成、退款与滥用。

## 11. 代码结构的渐进目标

现在不要直接大迁移。先补测试和契约，再逐步抽离：

```text
apps/
  web/
  mobile-capacitor/
  harmony-next/
  desktop-tauri/
packages/
  domain/       领域类型与不变量
  rules/        确定性结算
  events/       事件与投影
  memory/       记忆端口与适配器
  ai/           模型、Jev 与提示词适配
  ui/           共享展示组件
content/
  jiuxiao/      Canon、内容包和资源
services/
  api/          账号、权益、AI 网关、云存档
```

迁移顺序：`work/` 单一源码基线→抽 `domain` 纯函数→抽规则/事件→引入构建系统→再拆应用壳。禁止边修 0 号试玩边全面重写。

## 12. 双人错峰机制

```text
Sprint N
合作者：定义 N+1 的体验、Canon 和验收场景
你：实现 N 的契约、代码、测试和证据

Sprint N 结束
合作者：完成 N 的产品验收
你：完成 N+1 的技术风险审查
```

每周 45 分钟共同评审只处理：

1. 真实可运行增量；
2. 产品/Canon 结论；
3. 工程/风险结论；
4. 下周最多两个并行目标；
5. 一个共同验收场景。

聊天不是唯一需求来源。结论必须进入 Issue、PR 或 ADR。

## 13. GitHub 操作规则

### 13.1 分支与 PR

- `main` 始终可构建；
- 禁止两人直接向 `main` 同时推送；
- 每个 PR 只解决一个 Issue；
- 代码 PR 由合作者做产品语义检查；
- Canon PR 由你做数据结构和影响检查；
- 自动测试通过不等于产品验收通过。

建议分支：

```text
product/<topic>        产品、Canon、验收规格
codex/feat-<topic>     正式功能
codex/fix-<topic>      单一缺陷
codex/research-<topic> 有明确退出条件的实验
release/<version>      发布收尾
```

### 13.2 Project 状态

```text
Backlog → Spec Ready → In Progress → PR Review
        → Technical Verification → Product Acceptance → Done
```

Issue 必须写：问题、用户价值、范围内、范围外、主责、审查人、输入证据、验收、风险和证据等级。

### 13.3 决策记录

以下事项必须写 ADR：

- Mem0 是否进入生产；
- Jev 是否进入主链；
- 记忆模式与衰减参数；
- Capacitor、ArkWeb、Tauri 的选择；
- 商业模式与后端边界；
- 存档 Schema 破坏性变更；
- 平台化启动门槛。

## 16. 结构性风险

| 风险 | 严重性 | 控制 |
| --- | --- | --- |
| AI/记忆模型改写世界事实 | 致命 | 事件与状态单一权威源 |
| “遗忘”删除关键事实 | 致命 | 只衰减 NPC 检索，不删世界真相 |
| Jev 被误当规则引擎 | 高 | 有限候选、置信升级、规则复核 |
| 开放世界提前展开 | 高 | 先节点地图和单场景垂直切片 |
| 多端同时开发拖死核心 | 高 | Web→移动壳→Harmony→桌面顺序门禁 |
| 含 AI 订阅成本失控 | 高 | 配额、路由、缓存、单位经济模型 |
| 原生壳因“网站复刻”被拒 | 高 | 原生能力、离线、文件、通知和应用级体验 |
| 私人世界书/记忆外传 | 高 | 数据分类、明确同意、最小上传与删除能力 |
| 平台化固化错误接口 | 高 | 第二题材验证后才抽 SDK |
| 两人形成两个架构中心 | 中高 | 权威矩阵、ADR、双钥匙发布 |
