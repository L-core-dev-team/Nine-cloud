## 4. SECURITY DEFINER、角色与删除/fence

复核发现旧候选两个SECURITY DEFINER函数仍有默认PUBLIC EXECUTE，已在新0023撤销。最终目录证据：

|函数|所有者|EXECUTE授权（除owner）|搜索路径|
|---|---|---|---|
|lock_narrative_writer_fence_v2(text)|jiuxiao_narrative_schema_owner|jiuxiao_narrative_runtime|pg_catalog, public, pg_temp|
|narrative_erasure_allowed(jsonb)|jiuxiao_narrative_schema_owner|runtime、erasure|pg_catalog, public, pg_temp|

schema_owner与三个职责角色均校验NOLOGIN且无superuser/CREATEDB/CREATEROLE/BYPASSRLS。schema_owner具备函数需要的有限读取权限及fence所有权，应用不能切换为它。两个函数只执行固定查询；权限判断使用session_user，进入SECURITY DEFINER不会把调用者当作运维或删除角色。

专项另发现并真实复现更关键的缺陷：旧候选的search_path未显式放置pg_temp，应用创建同名临时归属表后，能让managed无G在COMMIT异常获准。旧证据明确记为 expected DB_REJECT / actual ACCEPT / safety FAIL；不能因旧37项通过就忽略它。

最终0023将新函数和触发器搜索路径固定为pg_catalog,public,pg_temp；对复用的6个0022辅助函数通过新迁移ALTER FUNCTION设置同样路径，历史0022文件原字节不改。相同应用角色的临时表遮蔽反例现在被COMMIT完整性检查拒绝，数据回滚。临时fence表也不能伪造真实fence。

非管理员grpf_untrusted被拒绝调用两个SD函数；gr01_app不能改函数owner、在public建表或SET ROLE为operator/eraser/schema_owner，不能写fence。只有gr01_operator可写入测试运维证明；应用通过专用函数持有读锁，不获得表UPDATE权限。仅给应用列级UPDATE(singleton)时，启动预检同样拒绝，随后撤权。本轮对启动检查补入has_any_column_privilege，避免漏掉列授权。

真正的删除操作GUC也不能授权普通应用删除归属；不存在/不匹配/未到ready/过期证明不通过。独立gr01_eraser配合法定owner绑定、有效delete/ready操作及账号/存档锁，可执行完整删除。组件回归覆盖现有会话绑定验证码关闭/删除、定期到期删除及导出。安装器管理员仅负责创建测试数据库、角色和授权夹具；实际登记、拒绝、worker、删除及运维操作分别使用应用、删除和运维登录，未用管理员测试代替。
