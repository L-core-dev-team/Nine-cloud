## 3. 硬性前置与阻断（按出现顺序）

| 序 | 阻断项 | 谁能解 | 现状 |
| --- | --- | --- | --- |
| 1 | `PUBLIC_API_BASE_URL_PENDING` | 采购公网地址 | 无 |
| 2 | 运营主体、正式域名、托管地、事故联系人、备份策略 | 责任人书面确认（`EXT-01`） | 未启动 |
| 3 | G-03 正式规则签署（否则回合永远 503） | LYL + Bird | 缺失值未补 |
| 4 | G-05 媒体权利凭证（否则 release 构建失败） | 权利人 | `LICENSE_PENDING` |
| 5 | G-04a Canon 双作者同摘要回执 | LYL + Bird | `CANON_RECEIPTS_PENDING` |
| 6 | 真实邮件投递到达（G-06） | 真实发件域 + 生产 SMTP | 仅预检通过 |
| 7 | ICP / 公安 / 生成式 AI 登记 | 境内主体 + 属地审批 | 未启动 |

> P0 不需要服务器；P1 需要主机，P2/P3 还需要真实 HTTPS 地址和可登录主机。G-03、G-04a、G-05、G-06 与境内备案只在对应云端回合、真实邮箱、受许可媒体或境内公测路径启用前成为门禁，不能把它们统称为“公测前”再跳过路线 A/B 的配置矛盾。

### 3.1 源码核验发现的实施阻断

以下不是一般验收缺口，而是按现有文件直接执行会失败或越过身份边界的配置冲突。解除前不得把 P2/P3 标记为完成。

| 阻断 | 实际依据 | 解除条件 |
| --- | --- | --- |
| 默认路线 A 与生产 Compose 不一致 | `deployment/api-production.compose.yml` 固定 `AUTH_ENABLED=true`、`AUTH_MAIL_PREFLIGHT=true`，并要求 SMTP 与前端 Origin。服务因此挂载邮箱账号接口；这不等于“不开在线账号”。 | 由两位作者签署路线选择。若保留 A，先补一份经批准的入口封锁规则和 SMTP 预检方案；若改走 B，先完成人工数据政策、真实邮件资源与 G-06。不得只隐藏前端登录按钮。 |
| 宿主 PostgreSQL 回环地址对 Compose 容器不可达 | `migrate` 与 `api` 加入 Compose bridge 网络；容器内 `127.0.0.1` 指向容器自身。宿主 PostgreSQL 仅监听 `127.0.0.1` 时，当前 P2 没有容器到宿主的连接路径。 | 首选在宿主提供受限 TCP 转发，只监听实际 Compose bridge 网关并转发到 `127.0.0.1:5432`；防火墙仅允许该 Compose 子网访问转发端口，公网仍不得开放 `5432`。若宿主无法满足，停止并提交新 ADR，不要放宽到公网监听。 |
| T1 同源路径转发尚无可执行配置 | Web 客户端使用相对路径 `fetch('/api/…')`；当前 `deployment/README.md` 提到的 `VITE_API_BASE_URL` 没有被该客户端读取。P3 还会在根路径请求 `/health` 与 `/ready`。 | 前端边缘入口必须把同源 `/api/*`、`/health`、`/ready` 转发到 VPS API，并保持 `Origin`、`Cookie` 与长请求超时；P3 的 `PUBLIC_API_BASE_URL` 指向用户实际访问的同源 HTTPS 根地址。 |
| 代理 IP 可信链尚未定义 | API 只接受最多 8 个精确 IP 作为可信代理，不接受 CIDR；被信任的直连代理可提供 `X-Forwarded-For`。 | 若使用 Cloudflare 橙云，Nginx 按官方 IP 段校验来源并还原访客 IP；API 只信任实际 Nginx 到 API 的精确内网对端地址。限制 origin 入口并验证伪造转发头不会改变限流身份。不得把 Cloudflare CIDR 填入 API 变量。 |
| P4 的云档测试顺序越过数据政策门禁 | P4-8 包含云档上传；P4-9 才放置政策。生产 `PolicyCloudSaveRepository` 在有效政策缺失或过期时拒绝写入。 | 批准并加载数据政策后，才允许任何生产云档写入；先验邮箱到达和会话，再在 P5 做云档读写。 |
| P0 评审产物不是生产发布批准或 API 镜像 | 当前 CI 的镜像只用于该 SHA 的冒烟，产物生成器明确写入 `releaseApproved:false`；上传清单没有生产镜像。 | P0 只证明该 SHA 的工程审阅包。P2 必须从干净的 `$SHA` 检出构建镜像、记录并核对镜像 digest；人工/发布批准仍是独立门禁。 |

> Docker Compose 默认给服务建立 bridge 网络。Docker 官方文档说明，容器访问宿主服务需要显式 host-gateway 或可达的宿主接口；本方案保持 Compose 文件不变，因此采用上表所述的宿主受限转发。数据库仍只监听回环地址。具体转发与防火墙规则必须在实际服务器上核验后才能启动迁移。

## 4. 逐阶段执行手册

> 约定：`$SHA` = 当前 RC 提交；所有命令在**仓库根目录**执行；`deployment/api.private.env` 由部署负责人独占维护。

### P0 · 制品与基线（不接触任何服务器）

| 步 | 命令 | 期望 | 失败处理 |
| --- | --- | --- | --- |
| P0-1 | `git status -sb && git rev-parse HEAD` | 工作区状态已知，`$SHA` 确定 | 若工作区 dirty，先确认是否影响制品；不得用本地构建代替 CI 产物 |
| P0-2 | 打开 GitHub Actions，确认 `head_sha == $SHA` 的 run 全绿 | 绿灯；当前工作流只在 PR 与推送到 `main` 时触发 | 若该 SHA 没有完整 run，停止；不得拼接不同提交的绿色步骤 |
| P0-3 | 下载产物 `jiuxiao-engineering-review-$SHA` | 含 `review-bundle/RC_MANIFEST.json`、`artifact-manifest.sha256` | 缺文件即视为无证据。该包是工程评审包，不是已批准发布包，也不含可直接部署的 API 镜像 |
| P0-4 | 记录指纹 | `RC_SHA` / `ARTIFACT_HASH` / `CANON_DIGEST` / `DB_SCHEMA_VERSION` / `BUILD_ID` / `CI_RUN` | 缺失项记「未知」，不得推断；不要把 `releaseApproved:false` 改述为发布批准 |

**出口**：六个指纹齐全且可复核。

### P1 · 主机准备（境外内测期）

| 步 | 命令 / 操作 | 要点 |
| --- | --- | --- |
| P1-1 | 采购轻量服务器（推荐 2核4G，首年约 ¥199） | **记录固定公网 IP**；此 IP 后续可能需申请模型服务商白名单 |
| P1-2 | 安全组只放行 `22/80/443` | **不得**放行 8787、5432 |
| P1-3 | 装 Docker 并配置镜像加速 | 国内宿主机必配 `registry-mirrors`，否则拉取超时 |
| P1-4 | 装 PostgreSQL 17（**宿主机自托管，不进 compose**） | 监听仅 `127.0.0.1`；建库建用户并只授本库权限。API 容器不能用容器内 `127.0.0.1` 连接它 |
| P1-5 | 建只读运行目录 | `sudo install -d -o root -g root -m 555 /run/jiuxiao`（容器内映射为 `/run/jiuxiao`） |

| --- | --- |

### P4 · 身份、邮件与规则接线（仅路线 B）

| 步 | 操作 | 校验 |
| --- | --- | --- |
| P4-1 | 设置 `AUTH_ENABLED=true` | 不设则规则插件不加载（见 `COUPLE-AUTH-RULES`），且 `/api/auth/*` 返回 **404** |
| P4-2 | `AUTH_PUBLIC_ORIGIN` = **前端 origin** | 必须是 `https://`；不能有路径或**末尾斜线**；不是 API 地址 |
| P4-3 | `AUTH_SECRET` | ≥32 字节；勿用占位值 |
| P4-4 | `AUTH_MAIL_FROM` / `SMTP_URL` | 587 用 `smtp://`，465 用 `smtps://`；**账号密码须 URL 编码** |
| P4-5 | `AUTH_TRUSTED_PROXY_ADDRESSES` | 逗号分隔、**≤8 项**、每项合法 IP；见 §6.2 |
| P4-6 | **SMTP 连接预检**：`node --env-file=.env scripts/verify-auth-mail.mjs` | 需**先 build**（脚本 import `apps/api/dist/`）；只查 DNS/TCP/TLS/AUTH，**不发信、不打印凭据**。期望输出 `{"status":"SMTP_CONNECTION_VERIFIED","delivery":"NOT_TESTED"}`。若 `AUTH_ENABLED≠true` 会失败并输出 `AUTH_DISABLED` |
| P4-7 | 启动期预检：`AUTH_MAIL_PREFLIGHT=true` 后重启容器 | 启动阻塞做连接检查；**成功不等于投递成功** |
| P4-8 | 放置经批准的 `ACCOUNT_DATA_POLICY` JSON 并设 `ACCOUNT_DATA_POLICY_PATH` | 生产必填；确认版本、期限、双作者批准与冷备依据有效。任何云档写入前必须完成 |
| P4-9 | **真实邮件投递验收（G-06 的唯一有效证据）** | 用授权测试邮箱发一次 → **查收件箱与垃圾箱** → 验证 → 查 session → 注销后确认 401。不要在本步上传云档 |
| P4-10 | 放置规则模块 | `runtime/rules.mjs`；`TURN_RULES_MODULE=/run/jiuxiao/rules.mjs`（**必须是本地绝对路径**） |

> ⚠️ `AUTH_MAIL_PREFLIGHT` 与 `verify-auth-mail.mjs` **都只验证连接**。邮件服务商返回「已接受」不等于进收件箱；`send()` 会在日志记 `PROVIDER_ACCEPTED`，那仍不是到达证明。

### 5.1 规则插件骨架（`/run/jiuxiao/rules.mjs`）

> 部署负责人安装；**由 LYL/Bird 提供的已签署规则**填充。缺任一函数或 `initialState` 不合约，**进程在启动时即失败**——这是设计意图，不是故障。

```js
// /run/jiuxiao/rules.mjs —— 绝对路径、.mjs、default export
export default {
  // 1) 规则提供者：需含 resolve()
  provider: {
    version: 'ActionRulesVersion/…',      // 必须与签署版本一致，否则 RULE_VERSION_MISMATCH
    resolve(/* action, worldState */) { /* 返回 accept / reject / clarify + 结果 */ },
  },
  // 2) 事件授权：决定某 DomainEvent 可授予哪些资源
  grantsForEvent(/* event, worldState */) { /* → grants */ },
  // 3) NPC 观测策略：谁能看到这条事件
  policyForNpc(/* event, worldState */) { /* → 可见范围 */ },
  // 4) 建档初始状态：返回值会过 WorldStateSchema.parse
  initialState({ ownerId, saveId, choices }) {
    return { /* 必须严格符合 WorldState 契约；不得用客户端 name/goal 直接授予修为或资源 */ };
  },
};
```

放置位置：宿主 `runtime/` 目录（容器内映射为 `/run/jiuxiao`），权限只读。`TURN_RULES_MODULE=/run/jiuxiao/rules.mjs`。

### 5.2 数据政策模板（`ACCOUNT_DATA_POLICY_PATH`）

> 下列**数值是拟定值**（源自 `LYL-05`），**必须由运营主体书面确认后**才可写入；不得把模板值当作已批准。

```json
{
  "version": "data-policy-2026-10-03.v1",
  "expiresAt": "2026-12-31T23:59:59Z",
  "approvedBy": ["LYL", "Bird"],
  "maxSaves": 20,
  "perSaveBytes": 1048576,
  "totalBytes": 10485760,
  "trashRetentionDays": 30,
  "backupPolicy": "<此处必须填写托管方冷备期限与清除依据的书面引用，不可留空>"
}
```

校验规则（不满足即 `INVALID_DATA_POLICY`）：`approvedBy` **必须同时含 `LYL` 与 `Bird`**；`perSaveBytes ≤ totalBytes`；三个字节/数量字段须为安全整数且 ≥1；`trashRetentionDays` 0–3650；`expiresAt` 过期即 `DATA_POLICY_NOT_READY`。

### 5.3 叙事配置模板（`NARRATIVE_CONFIG_PATH`）

> 依据 `deployment/narrative.example.json`。**所有岗位默认关闭**；`story` 标 `required: true` 但 `enabled: false` 意味着「不启用叙事」是合法起点。

```json
{
  "story": {
    "enabled": true,
    "required": true,
    "dependencies": [],
    "timeoutMs": 20000,
    "maxOutputTokens": 4096,
    "retries": 1,
    "primary": {
      "protocol": "openai-chat",
      "baseUrl": "https://<已批准供应商端点>",
      "model": "<已批准的真实 Model ID>",
      "keyEnv": "NARRATIVE_KEY_STORY"
    }
  }
}
```

- 其余四岗位按同样结构追加；`dependencies` 只能引用已成功的前置岗位。
- `timeoutMs` 需与反代 `proxy_read_timeout` 协调（后者已设为 180s，勿大于它）。
- 相关错误码：`NARRATIVE_CONFIG_TOO_LARGE`、`INVALID_NARRATIVE_ROLE`、`INVALID_NARRATIVE_SLOT`。

## 6. 反代配置样例

### 6.1 Nginx 要点

```nginx
location /api/ {
    proxy_pass         http://127.0.0.1:8787;
    proxy_http_version 1.1;
    proxy_set_header   Host              $host;
    proxy_set_header   X-Real-IP         $remote_addr;
    proxy_set_header   X-Forwarded-For   $proxy_add_x_forwarded_for;
    proxy_set_header   Origin            $http_origin;

    proxy_connect_timeout 10s;
    proxy_read_timeout    180s;   # 必须 > 回合服务 120s
    proxy_send_timeout    180s;

    proxy_buffering  off;         # 回合为长响应
    proxy_cache      off;         # 认证路径禁止缓存
}
```

- `X-Forwarded-For` 只有在 `AUTH_TRUSTED_PROXY_ADDRESSES` 含反代地址时才会被采信（取**最后一段**）。
- 必须透传 `Origin`，否则写操作会得 `403 ORIGIN_REJECTED`。

### 6.2 `AUTH_TRUSTED_PROXY_ADDRESSES` 取值表

| 链路 | API 看到的 socket 地址 | 配置值 |
| --- | --- | --- |
| 同机 Nginx → `127.0.0.1:8787` | `127.0.0.1` | `127.0.0.1,::1` |
| Cloudflare → 源站 | 边缘节点 IP | Cloudflare 官方 IP 段（注意 **≤8 项上限**，按需取子集） |
| 独立反代机 | 反代机内网 IP | 该反代机地址 |
| 直连（无反代） | 真实客户端 IP | 留空 |

> **漏配的后果**：所有请求被视为来自同一 IP，IP 限流（60/小时）会把全部用户算作一个人。

## 7. 故障排查手册

| 现象 | 定位 | 处理 |
| --- | --- | --- |
| `/api/auth/code` 返回 **404** | `AUTH_ENABLED ≠ 'true'`，`mountAuth` 未挂载 | 开启认证；404 在此表示「功能不存在」，不是权限问题 |
| 冒烟报 `PUBLIC_HTTPS_API_REQUIRED` | `PUBLIC_API_BASE_URL` 缺 scheme/带路径/指向本地 | 必须为 `https://host/`，pathname 恰为 `/` |
| 冒烟报 `API_SMOKE_FAILED` | 三项中某项状态码不符；或服务在跳转 | 检查是否在 http→https 跳转（`redirect:'error'` 会直接失败） |
| `verify-auth-mail.mjs` 报 `AUTH_DISABLED` | 该脚本同样要求 `AUTH_ENABLED=true` | 补齐认证配置后再跑 |
| `verify-auth-mail.mjs` 报 `MAIL_PREFLIGHT_FAILED` | DNS/TCP/TLS/AUTH 任一失败 | 核对 host/端口/协议/URL 编码后的凭据 |
| `PRIVATE_DATABASE_AND_APPROVED_POLICY_REQUIRED` | 缺 `DATABASE_URL` 或 `ACCOUNT_DATA_POLICY_PATH` | 补齐；脚本不会输出细节 |
| `Cannot find module '../apps/api/dist/...'` | 未 build 就跑运维脚本 | 先 `pnpm --filter @jiuxiao/api build`，或直接在容器内执行 |
| 容器反复重启，日志出现 `Production authentication requires HTTPS` | `AUTH_PUBLIC_ORIGIN` 非 https | 改证书与 origin；生产不接受 http |
| `Invalid AUTH_TRUSTED_PROXY_ADDRESSES` | 超过 8 项或含非 IP | 精简为 IP 列表 |
| `SMTP port 465 requires smtps://` | 协议与端口不匹配 | 465 配 `smtps://`；587 配 `smtp://` |
| `TURN_PLUGIN_LOCAL_PATH_REQUIRED` | `TURN_RULES_MODULE` 指向远程或非绝对路径 | 改容器内绝对路径 `/run/jiuxiao/rules.mjs` |
| 回合恒返 `503 RULES_NOT_READY` | 未开 `AUTH_ENABLED`、无规则模块、或规则未签署 | 三者逐一确认；**这是 fail-closed 正确行为** |
| 回合偶发被截断 | 反代读超时 < 120s | 调 `proxy_read_timeout` |
| 登录成功但刷新即掉线 | Cookie 未落地 | 查 `SameSite`/`Secure`/`Domain`；确认前端与 API **同站** |
| 验证码提示过于频繁 | `AUTH_TRUSTED_PROXY_ADDRESSES` 漏配 | 按 §6.2 配置 |
| 写操作全部 403 | `Origin` 不精确等于 `AUTH_PUBLIC_ORIGIN`（含末尾斜线也会不等） | 核对前端 origin；反代须透传 `Origin` |
| `/ready` 返回 503 | 数据库不可达或 `DATABASE_URL` 错 | 查 `pg_isready`；容器内自查 |
| 迁移失败 | 未先备份 | **绝不**在未备份时重跑；先隔离库演练 |
| 到期任务无任何邮件 | 设计如此 | 计划任务不发信（`SCHEDULED_JOB_DOES_NOT_SEND_MAIL`），需另设告知路径 |
| 启动即 `INVALID_TURN_PLUGIN` | 插件缺四项之一，或 `initialState` 不合约 | 对照 §5.1 骨架逐项补齐；**不要**放宽校验 |
| 启动即 `INVALID_DATA_POLICY` | 政策 JSON 字段缺失/越界/未含 LYL+Bird | 对照 §5.2 模板；注意 `perSaveBytes ≤ totalBytes` |
| `DATA_POLICY_NOT_READY` | 政策缺失或 `expiresAt` 已过 | 换新政策版本，**不要**改代码绕过 |
| `CLOUD_QUOTA_EXCEEDED` | 单档超限、总量超限或新建达上限 | 属正确门禁；先导出清理，**不要**提额绕过 |
| `NARRATIVE_CONFIG_TOO_LARGE` / `INVALID_NARRATIVE_ROLE` / `INVALID_NARRATIVE_SLOT` | 叙事配置过大/岗位名非法/槽位结构非法 | 对照 §5.3；岗位名必须属于已批准五岗位 |
| `RULE_VERSION_MISMATCH` / `RULE_VERSION_REQUIRED` | 存档携带的规则版本与插件不一致或缺失 | 说明该存档来自不同规则版本；**需走迁移**，不可改版本号糊过去 |
| 回合 500/503 但配置看起来正确 | 多半是 `RULES_NOT_READY`（规则未签署）或缺少插件 | 见 §7 前两行与 §10.1 耦合说明 |

## 10. 身份、隐私与登录闭环

> 本节由原《内测环境方案》§5 合并而来。**执行顺序上先读 §4 的 P4，再回到本节查细节。**

### 10.1 两条身份路线

| 路线 | 做法 | 能验证 | 代价 |
| --- | --- | --- | --- |
| **A · 纯游客** | 不开放在线账号；全本地 + 手动导出/导入 | UI、玩法游客闭环、旧档迁移、场景与画质、媒体回退、真机 | 不发送验证码；当前 Compose 仍要求 SMTP 连接预检，供应商固定费用尚未计入 |
| **B · 同源部署 + 真实邮箱** | 前端与 API 同站/同源；配真实发件域与生产 SMTP | 云档、双账号隔离、CAS 冲突、权威回合事务、账号生命周期 | 需域名与发件域；需真实验收 |
| **C · 测试凭据** | 虚构邮箱 + 预检型 SMTP | 只证明投递链路可跑 | **不解决 Cookie 问题**，且不得把测试值部署为生产凭据——**不可单独采用** |

> 🔴 **代码级硬耦合（决定路线顺序）**
>
> `apps/api/src/index.ts:31`：
> ```ts
> const plugin = emailAuth ? await loadTurnPlugin(process.env.TURN_RULES_MODULE) : undefined;
> ```
> `emailAuth` 来自 `createEmailAuthRuntime()`，而它在 `AUTH_ENABLED !== 'true'` 时**直接返回 `undefined`**（`services/auth-runtime.ts:14`）。
>
> **因此：不开启邮箱登录 ⇒ 规则插件不加载 ⇒ `runtime.rules` 为 `undefined` ⇒ 云端回合永久 `503 RULES_NOT_READY`。**
> 这不是配置偏好，是代码路径事实。**开启账号必须排在云端回合验收之前**（待签决定 D-I-07）。
> 附带效应：未开启认证时 `/api/auth/*` 根本不挂载，返回 **404**。

### 10.2 三种部署拓扑（术语已更正）

| 拓扑 | 前端改动 | CORS | Cookie | 结论 |
| --- | --- | --- | --- | --- |
| **T1 同源路径反代** | **零改动** | 不发生 | host-only + `SameSite=Strict` | **推荐**；`cloud-sync.ts` 用相对路径 `fetch('/api/…')`，天然成立 |
| T2 同站子域 | 需 base URL helper（PR #35，未合并） | 走（代码已实现） | host-only + `SameSite=Strict` 可用 | 多一次跨 origin 往返 |
| T3 Cloudflare Worker 同源转发 | 零改动 | 不发生 | 同 T1 | T1 的 CDN 变体；**须配 `AUTH_TRUSTED_PROXY_ADDRESSES`** |

> **术语澄清（此前表述不准确）**：**同源**＝scheme+host+port 全同；**同站**＝scheme 同且注册域同。`jiuxiao.tld` 与 `api.jiuxiao.tld` 是**同站不同源**——不触发第三方 Cookie 问题，`SameSite=Strict` 依然可用，但仍需 CORS。**本项目的卡点是「跨站」，不是「跨源」，因此不必为 Cookie 强行同源。**

### 10.3 登录闭环操作手册

**Cookie 规格（实现事实）**

| 属性 | 值 |
| --- | --- |
| 名称 | `jx_session` |
| 值 | `randomBytes(32).toString('base64url')`（43 字符）；库中只存 `sha256(token)` |
| 属性 | `Path=/; HttpOnly; SameSite=Strict; Max-Age=604800`，HTTPS 时追加 `Secure` |
| Domain | **无**（host-only，绑定下发 API 的主机） |
| 登出 | `revoke` + 以 `Max-Age=0` 下发空值 |

**参数**：六位验证码、十分钟有效期、五次失败上限、随机会话七天；验证码 `HMAC-SHA256(secret, "email\0code")`；`refresh` 轮换并立即吊销旧值。

**端到端时序**

| 步 | 请求 | 成功 | 失败 |
| --- | --- | --- | --- |
| 1 发码 | `POST /api/auth/code` `{email}` | `202 {status:'sent',resendAfterSeconds:60,expiresInSeconds:600}` | `400 INVALID_EMAIL` / `INVALID_REQUEST`；`429 RATE_LIMITED` + `Retry-After: 60`；`503` 于 `VERIFICATION_STORE_FAILED` / `MAIL_AUTH_FAILED` / `MAIL_UNAVAILABLE` / `MAIL_REJECTED`（含 `stage`、`requestId`，**不含服务商原始报错或凭据**）；未开认证为 **404** |
| 2 校验 | `POST /api/auth/verify` `{email, code}` | `Set-Cookie: jx_session=…` + `{account:{id,email}, expiresAt}` | `401 INVALID_OR_EXPIRED_CODE` |
| 3 查会话 | `GET /api/auth/session` | `200 {account, expiresAt}` | `401 UNAUTHENTICATED` |
| 4 刷新 | `POST /api/auth/refresh`（可带 `X-Jiuxiao-Account`） | 轮换：新 Cookie，旧 token 立即失效 | 账号头不匹配或无效 → `401` |
| 5 登出 | `POST /api/auth/logout` | `{status:'signed_out'}` + 清 Cookie | — |
| 6 恢复 | `POST /api/auth/restore`（`restore=true`） | 同 2 | 超宽限期或条件不满足 → 拒绝 |

**发码失败自动退额**：邮件失败时先 `invalidate(email,digest)` 再 `refundIssue(email,ip)`，避免限流配额被失败投递吃掉。

**Origin 与 CORS 硬约束**：`mountAuth` 对 `/api/*` 挂全局中间件——非 `GET/HEAD/OPTIONS` 请求的 `Origin` 必须**精确等于** `AUTH_PUBLIC_ORIGIN`（**不能有末尾斜线**），否则 `403 ORIGIN_REJECTED`；`OPTIONS` 预检只放行 `GET/POST/PUT/DELETE` 与 `Content-Type`/`X-Jiuxiao-Account`，其余 403。响应统一带 `Cache-Control: no-store` 与 `Vary: Origin`。

**客户端传输契约**：`apps/web/src/cloud-sync.ts` 使用相对路径 `fetch('/api/…')`、`credentials:'include'`、`cache:'no-store'`、`AbortSignal.timeout(20000)`、可选 `x-jiuxiao-account`。

**登录后的能力边界**

| 能力 | 接口 | 鉴权 |
| --- | --- | --- |
| 存档 | `GET/POST /api/saves`、`GET/PUT /api/saves/:saveId` | 会话解析出的 `ownerId`，**不信任客户端 owner** |
| 索引/回收站 | `GET /api/save-index`、`GET /api/save-trash` | 同上 |
| 权威建档 | `POST /api/games` | 返回服务端权威 `SaveEnvelope` |
| 提交回合 | `POST /api/turns` | `RULES_NOT_READY` 时拒绝结算 |
| 账号能力 | `GET /api/account/capabilities` | 未登录 401 |
| 全量导出 | `GET /api/account/export` | 会话 |
| 生命周期 | `POST /api/account/operation/{begin,verify,complete,cancel}` | 会话 + 验证码双挑战 |

写入类错误码语义：`REVISION_CONFLICT` / `SAVE_CONFLICT` = CAS 失败，**客户端必须让玩家选择，不得自动覆盖**；`UNAUTHENTICATED` = 会话失效；`RULES_NOT_READY` = 规则未签署，属正确行为。

**账号生命周期闭环**

| 操作 | 步骤 | 边界 |
| --- | --- | --- |
| 邮箱变更 | `begin`(旧)→`verify`(旧)→`begin`(新)→`verify`(新)→`complete` | 双挑战；换邮箱后旧码立即失效 |
| 关闭账号 | `begin`→`verify`→`complete` | 需 `ACCOUNT_DATA_POLICY_VERSION`；**关闭后全部 Session 吊销**；软删入回收站 |
| 主动恢复 | `POST /api/auth/restore` | 仅本人邮箱 OTP，**仅宽限期内**；普通登录**不自动恢复** |
| 全量导出 | `GET /api/account/export` | 与删除流程独立，随时可用 |
| 永久擦除 | 计划任务 `api-account-expiry.mjs --apply` | 需 `ACCOUNT_DELETE_ENABLED=true`（默认 false）+ 政策未到期；每批 ≤100；**不发信**；冷备擦除须运营方另出工单 |

**其他登录方式**：当前**没有**（无 OAuth / 微信），符合 ADR-0003「不引入另一套应用框架」。若将来考虑，须先写 ADR；第三方身份不得成为 `ownerId` 唯一来源；会引入新的个人信息处理者与跨境传输方；**不得削弱 `HttpOnly` + `SameSite` 契约换便利**。1.0 内属范围变更。

### 10.4 个人信息红线

- 路线 A 下**零真实个人信息**：不使用真实手机号、身份证、支付信息。
- 问卷原始数据中的联系方式**不得**导入内测环境；候补沟通走私聊。
- 参与者存档、截图、日志按私密层级保管，不进公开仓库、不进发行包。
- 对话内容不得用于模型训练，除非参与者单独书面同意。

### 10.5 登录验收清单

- [ ] `jx_session` 为 host-only + `HttpOnly` + `SameSite` + `Secure`
- [ ] 登录请求实际携带 Cookie（Network 面板确认），刷新后会话仍在
- [ ] 连续两次 `refresh` 后旧 token 立即失效
- [ ] 登出后 Cookie 被清空，**本地存档与未完成队列仍在**
- [ ] 连续发码命中 `429` + `Retry-After: 60`
- [ ] 邮件失败时限流配额被退额
- [ ] 账号 A 读不到账号 B 的任何存档，且不泄露存在性
- [ ] 邮箱变更 / 关闭 / 恢复各走一遍并留脱敏记录
- [ ] 手机真机（iPhone Safari）实测会话保持；**桌面浏览器结果不可替代**

2. **境内服务器规格**：初期 2C2G 够；并发上升需升配。
3. **R2 10 GB**（若迁媒体上去）。
4. **Workers Free 的 10 ms CPU/请求**——长任务（叙事、导出）会先撞 CPU 上限而非请求数上限【待核】。

### 11.6 省钱纪律（按收益排序）

1. 保持 BYOK，服务端不垫任何 AI 费用。
2. 保持 ADR-0004，不开收费、不接支付。
3. PostgreSQL 自托管。
4. 媒体留构建产物内，不迁对象存储/CDN。
5. Workers 保持 Free 档。
6. 不买邮件独立 IP（$128/月）。
7. 域名长续期；服务器选同价续费机型。
8. **不要用「免费额度」承载唯一副本**——数据必须有异机备份。

## 12. 应用商店上架（范围变更，需新 ADR）

> ⚠️ 与[重建总方案](九霄1.0公测版重建总方案.md) §9 冲突：总方案写明「Web/PWA 是 1.0 正式分发；原生安装包不在此版声称已通过」。列为 1.0 完成条件属**范围变更**，须另写 ADR。

### 12.1 分清两件事

响应式 Web + PWA 已能覆盖「装到桌面、离线打开、更新可控」。商店上架额外带来**系统级分发与发现**，以及一整套**独立准入体系**。**结论：商店上架是渠道增量，不是上线前提**；设为 1.0 完成条件会把周期从「月」量级拉到「年」量级——瓶颈不是技术，是资质审批。

### 12.2 iOS App Store（中国区）

| 项 | 要求 | 九霄处境 |
| --- | --- | --- |
| 开发者账号 | 企业 **$299/年**；个人 $99/年仅限纯离线免费工具，**禁止带注册/付费/广告/社区/资讯** | **必须企业账号** |
| ICP 备案号 | 中国区新 App 必填，系统校验 App 名称与备案主体一致，不一致驳回 | 需境内服务器 + 主体 |
| 隐私政策 | 独立域名网页；首次打开弹窗同意；不得内嵌 | 需公开政策页 |
| 公安联网备案 | 上线 30 日内 | 与网站同一链路 |
| 账号删除 | 应用内必须有删除入口 | 已有 `/api/account/operation/*` |
| 审核测试账号 | 须完成登录→浏览→操作→退出全流程 | 需提供可用账号 |
| **网络游戏版号（ISBN）** | 中国区游戏类需要 | ⚠️ **最高阻断项** |
| 审核周期 | 约 17 个工作日 | 需预留缓冲 |

### 12.3 鸿蒙 AppGallery

| 项 | 要求 | 九霄处境 |
| --- | --- | --- |
| 开发者账号 | 个人实名或企业认证（营业执照） | 需主体 |
| **应用创建受邀名单** | 2026 起收紧，新账号需邮件申请（`agconnect@huawei.com`） | ⚠️ 新增门槛 |
| **软件著作权** | **强制**；审核 20–40 工作日 | ⚠️ 须尽早启动 |
| **APP 备案（鸿蒙版）** | 接入商系统选「鸿蒙」平台并填鸿蒙包名；**包名创建后不可改** | 需境内服务器 |
| **AI 生成合成内容** | 须提供资质；生成内容须加**显式标识 + 文件元数据隐式标识** | ⚠️ 与生成式 AI 备案强耦合 |
| 性能基线 | 冷启动 ≤800ms；内存峰值 ≤30% 设备内存；连续 60 帧波动 ≤5% | ⚠️ WebView 套壳高风险 |
| UX | 文本与背景对比度 ≥3 | UI 1.0 需补自动检查 |
| 隐私 | 首次启动弹窗；**同意前不得收集个人信息** | 需新增首启同意流程 |
| 版本一致性 | 「已有面向用户的其他版本时，鸿蒙版本应保持不低于其质量」 | 双线并行 |
| 审核周期 | 1–7 个工作日 | — |

### 12.4 最致命的阻断项

1. **纯血鸿蒙不能直接复用 Android APK**。华为提供 ArkWeb Web 组件，可作为嵌入网页的技术候选；它不证明九霄的安装包、体验或审核路径可行。须在目标版本真机验证后再决定原生重写或 Web 容器方案。
2. **iOS 中国区游戏版号（ISBN）** 是最高不确定项：Apple 如何归类（游戏 vs 工具/娱乐）决定是否必须版号【待核】。
3. **AI 内容标识是双平台共同要求**，且与生成式 AI 备案是同一套材料链；备案没做完，商店「AI 资质」栏填不出来。

### 12.5 工程侧必须新增（当前仓库完全没有）

1. **原生壳**：iOS WKWebView 或 Capacitor/Tauri；鸿蒙 ArkTS + ArkUI。
2. **桥接层**：IndexedDB 在壳内的存储映射。
3. **BYOK 密钥安全存储**：Keychain / 鸿蒙 KeyStore，**不得留在 WebView localStorage**（现为标签页内存）。
4. **冷启动优化**：壳启动到首屏可交互 ≤800ms。
5. **离线包与更新**：审核版本与线上版本分离，更新不得绕过审核。
6. **首启隐私同意流程**：两平台都要求，UI 1.0 当前没有。
7. **AI 内容显式 + 隐式标识**。
8. **审核测试账号与审核说明**。
9. **响应式适配真机重测与留证**。

### 12.6 成本与周期增量

| 项 | 一次性 | 年度/持续 |
| --- | --- | --- |
| Apple 企业开发者账号 | — | **$299/年** |
| 华为企业开发者账号 | — | 一般免费（需企业认证）【待核】 |
| 软件著作权登记 | 20–40 工作日 | — |
| **网络游戏版号** | 数月，费用高【待核】 | — |
| ICP / APP 备案（含鸿蒙版） | 各约 20 个工作日 | — |
| 原生壳开发（iOS + 鸿蒙） | 数人月 | 每年 OS 版本适配 |

> 对照 §11.3：公测期服务器与域名约 **¥13/月（首年）→ ¥53/月（续费）**；而 T0 纯游客可做到 **¥0**。**在版号与软著解决前，商店上架的合规与研发成本是它的数十倍以上。**

### 12.7 建议分期

| 里程碑 | 内容 | 前置 |
| --- | --- | --- |
| **M0** | 响应式 Web + PWA 公测（维持现行总方案路线） | 境内服务器 + ICP + 生成式 AI 登记 |
| **M1** | 软著与 APP 备案**启动**（周期长，与 M0 并行） | 运营主体就位 |
| **M2** | iOS 上架（先判定版号是否必要） | M1 + 企业账号 + 测试账号 |
| **M3** | 鸿蒙上架（ArkTS 重写，或先以**元服务**切入） | M1 + 受邀名单 + 性能达标 |

**元服务（Meta Service）** 可列为鸿蒙侧候选；功能范围、审核口径与研发成本须经官方规则核对和原型评估，现阶段不作成本比例或上架周期承诺。

### 12.8 商店专项待核

1. 九霄在 Apple 归类为「游戏」还是「工具/娱乐」——**直接决定是否需要版号**。
2. AI 生成文字 + 文字 RPG 的内容标识具体规范。
3. 鸿蒙 Web 组件（XWeb）能否满足审核与性能基线。
4. 软著名称与应用名、包名的一致性口径。
5. 华为「应用创建受邀名单」的通过率与周期。
6. 审核期需后端可用 → 反向要求先完成境内生产部署。

## 14. 给模型的执行约束

1. 每次只推进**一个**阶段，不并行跨阶段改动。
2. 执行前先读本手册 §2 与目标阶段；执行后把实际命令、原始输出、指纹回填到阶段记录。
3. **不修改** §「不可变」清单中的任何文件；确需修改先写 ADR。
4. 任何「已完成」的表述必须附**可复算证据**（命令 + 输出 + 指纹），否则记为「已实现未验收」。
5. 遇到 §3 的阻断项，**停止并上报**，不得用降级、mock 或后门绕过。
6. 不在仓库、日志、截图、聊天中出现真实密钥、验证码、会话 token、玩家真实邮箱。
