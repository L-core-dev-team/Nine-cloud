## 1. 目标和结论

内测环境的目标只有一句话：**让 LYL 与 Bird 能在同一份制品上，把九霄真的玩一遍，并留下可复核的证据。**

它不是公测的预演缩微版，而是**证据生产环境**。因此本方案的全部设计围绕三条：

1. **单一制品、单一指纹。** 内测环境只运行一个 RC SHA。任何「先在本地看看，回头再上内测」的做法都会制造制品漂移，直接破坏 G-02 双签的前提。
2. **不引入任何境外数据风险。** 内测期**不开放邮箱注册**，不采集真实个人信息。身份退化为游客本地 + 手动备份（C/A/S），这既是合规要求，也让 Cookie 同源问题从根上消失。
3. **不越过任何 fail-closed 门禁。** `RULES_NOT_READY`、`LICENSE_PENDING`、`CANON_RECEIPTS_PENDING` 在内测环境中的处置方式与生产完全一致：要么满足条件后放行，要么保持拒绝。**内测环境没有任何「调试后门」。**

## 3. 环境拓扑

```
玩家（邀请制）
 │
 ├─ Cloudflare Pages                    [已有，前端独立任务]
 │    └─ 构建期注入 VITE_API_BASE_URL → 内测 API 公网地址
 │
 └─ 境外单节点 VPS（推荐：轻量 2核4G，首尔或同类）
      ├─ Caddy / Nginx  ──►  127.0.0.1:8787   （TLS + 反代，保留 Origin 与 Cookie）
      ├─ Docker Compose（deployment/api-production.compose.yml）★ 一行不改
      │    ├─ migrate   一次性，跑完退出
      │    └─ api       长驻，API_HOST=0.0.0.0 / API_PORT=8787
      ├─ PostgreSQL 17（宿主机自托管，**不进 compose**）
      ├─ /etc/jiuxiao/runtime        只读，规则模块与叙事配置
      └─ 计划任务：备份（pg_dump）+ 价格快照更新检查
```

**为什么 PostgreSQL 放宿主机而不是 compose**：production compose 只有 `migrate` 与 `api` 两个服务，数据库是外部 `DATABASE_URL`。把 PG 装在宿主机、`DATABASE_URL` 指向 `127.0.0.1:5432`，compose 保持原样。代价是备份要自己做，收益是**不改动已交接的部署契约**。

## 4. 不可变边界

以下项在本方案下**不因环境而放宽**：

- 不改 `deployment/api-production.compose.yml` 与 `docker-compose.yml`。
- 不改 `TURN_RULES_MODULE` 的只读挂载与「永不从客户端、模型或远程 URL 加载」的安全模型（`deployment/README.md:18`）。
- 不把 API 或生产 PostgreSQL 迁往 Vercel Functions / Cloudflare Workers / Supabase 等托管运行时。理由见可行性分析 DND-1。
- 不在容器内放真实密钥；密钥只在 `api.private.env`，权限限部署账号。
- 不关闭或放宽 `ACCOUNT_DELETE_ENABLED`（默认 `false`）。
- 不把 `AUTH_MAIL_FROM` / `SMTP_URL` 指向个人信箱。
- 不为内测单独编译一份「测试专用构建」——内测跑的必须是 RC SHA 本身的制品。

## 5. 身份与数据边界（内测期最关键的一节）

### 5.1 内测期不开放在线账号

| 项              | 内测期取值           | 理由                                |
| -------------- | --------------- | --------------------------------- |
| 邮箱 OTP 注册登录    | **关闭**          | 见 §5.2                            |
| `AUTH_ENABLED` | 视同 `false`      | 无账号即无会话依赖                         |
| 玩家存档           | 全部本地（IndexedDB） | ADR-0003 已批准游客完整本地                |
| 云同步            | 不开放             | `PUBLIC_API_BASE_URL_PENDING` 未解除 |
| 备份方式           | 手动导出/导入         | ADR-0003 已批准手动 CAS                |

**这不是偷懒，是当前唯一不需要处理跨站 Cookie 的形态。** `deployment/README.md:14` 写明：完全跨站需 `None + Secure`，而 Safari 可能阻止第三方 Cookie；[缺口清单](九霄1.0阶段缺口与人工交接清单-2026-09-29.md) PR #35 交叉复核也确认「独立 API 域名无法建立 Cookie 会话」。在内测期放弃在线账号，等于一次性绕过这个未解问题。

> ⚠️ **不要误读为「邮箱登录没做」。** 邮箱 OTP 登录是**已完整实现并有测试覆盖**的能力，本节「关闭」是**内测期的方案取舍**，不是能力缺失。现状与可选路线见 §5.4。

### 5.2 若确实需要在线账号（例外路径）

必须先满足全部条件，缺一不得开启：

1. 引入同源边缘层（Cloudflare Worker 同源转发，或把前端与 API 收敛到同一主域子域）；
2. 若走 Worker，**必须**把 Cloudflare 出口 IP 段加入 `trustedProxyAddresses`，否则 `SEC-02` 的 IP 限流会把所有请求识别为同一代理而失真；
3. 真实邮箱实际到达验收（G-06），不得以 SMTP 接受冒充收件箱到达；
4. 经批准的数据政策与配额外置生效（G-06 / `LYL-05`）。

### 5.3 个人信息红线

- 内测环境**零真实个人信息**：不使用真实手机号、真实身份证、真实支付信息。
- 问卷原始数据中的 3 份真实联系方式**不得**导入内测环境；候补沟通走私聊。
- 内测参与者的存档、截图、日志如需转交，按私密层级保管，不进公开仓库、不进发行包。
- 内测环境内的对话内容不得用于模型训练，除非参与者单独书面同意。

### 5.4 登录方式：现状、卡点与三条路线

**现状（已核实，非占位）**

邮箱验证码登录是完整实现：

| 层      | 已有内容                                                                                                                     |
| ------ | ------------------------------------------------------------------------------------------------------------------------ |
| API 路由 | `POST /api/auth/code`（发验证码）、`GET /api/auth/session`（查会话）、`POST /api/auth/refresh`（刷新并旋转吊销旧值）、`POST /api/auth/logout`（登出） |
| 服务     | `apps/api/src/services/email-auth.ts`；错误码 `INVALID_EMAIL` / `MAIL_UNAVAILABLE` / `VERIFICATION_STORE_FAILED`             |
| 参数     | 六位验证码、十分钟有效期、五次失败上限、随机会话七天                                                                                               |
| 凭据处理   | 验证码 HMAC、session token SHA-256，不落明文                                                                                      |
| Web 界面 | `routes/CloudSettings.tsx` 完整「发送验证码 → 输入 6 位码 → 登录」流程，含 `one-time-code` 自动填充、429 限流提示、登录后「云端备份需手动提交，本地存档始终保留」            |
| 账号生命周期 | `routes/AccountLifecyclePanel.tsx` 邮箱变更（旧邮箱 + 新邮箱双挑战）、关闭账号、全量导出、受控在线擦除                                                   |

**卡住的是生产条件与部署形态，不是功能**

| 卡点                                     | 性质    | 出处                                       |
| -------------------------------------- | ----- | ---------------------------------------- |
| `AUTH_ENABLED` 默认关闭                    | 配置默认值 | `deployment/api-private.env.example:7-8` |
| 需真实发件域、生产 SMTP、`AUTH_SECRET`、精确 Origin | 外部资源  | `EXT-01` / G-06                          |
| SMTP 预检**不发信**；「Provider 接受不等于收件箱到达」   | 验收边界  | ADR-0003:29                              |
| 真实邮件到达、双账号隔离、恢复演练未做                    | 验收缺口  | G-06                                     |
| 现有客户端仍 same-origin，跨站须显式配置并重验会话        | 部署形态  | ADR-0003:11                              |

**其他登录方式：目前没有，且不应引入。** ADR-0003 已定「沿用 Hono/PostgreSQL/Drizzle，不引入另一套应用框架」。当前身份体系只有两层：游客本地 + 邮箱 OTP。没有微信、没有 OAuth、没有第三方身份联邦——这是既定取舍，不是遗漏。

**三条可选路线**

| 路线                  | 做法                                                                                             | 能验证什么                                  | 代价                                                         |
| ------------------- | ---------------------------------------------------------------------------------------------- | -------------------------------------- | ---------------------------------------------------------- |
| **A · 纯游客**（本方案默认）  | 不开放在线账号；全本地 + 手动导出/导入                                                                          | UI 1.0、玩法 1.0 的游客零配置闭环、旧档迁移、场景与画质、媒体回退 | 最省（无邮件成本）；**验证不到云档与云端回合**                                  |
| **B · 同源部署 + 真实邮箱** | 前端与 API 收敛到同一主域子域（`jiuxiao.tld` / `api.jiuxiao.tld`），或用 Cloudflare Worker 做同源转发；配真实发件域与生产 SMTP | 云档、双账号隔离、CAS 冲突、权威回合事务、账号生命周期全链        | 需域名与发件域；需真实验收；**Worker 路线必须配 `trustedProxyAddresses`**     |
| **C · 测试凭据**        | 虚构邮箱 + 预检型 SMTP                                                                                | 只证明投递链路可跑通                             | **不解决跨站 Cookie**，且 ADR-0003 明令「不得把测试值部署为生产凭据」。**不可单独作为方案** |

**关键分叉：内测目标决定路线**

`routes/TurnWorkspace.tsx` 明确「请先登录云端账号；服务未开启时本地游戏资料仍可使用」。因此：

- 若内测只验证**本地玩法、UI、规则回放、媒体与降级** → 走 A。
- 若内测要验证**云档与权威回合事务**（即 S6 真正的价值所在）→ 必须走 B，且同源是前提，C 无法替代。

**建议**：先以 A 跑通 I0–I3（部署与冒烟），把同源子域与发件域在 I1 阶段就规划好；待 G-03 规则签署完成后一次性切到 B，避免二次采购与二次走查。

## 6. 媒体与素材边界

| 阶段条件                  | 内测期处置                                                            |
| --------------------- | ---------------------------------------------------------------- |
| `LICENSE_PENDING` 未销账 | 媒体继续走构建内静态资源（`apps/web/dist/scenes/candidate/`），**不接入 R2 运行时分发** |

## 7. 规则与叙事边界

| 项       | 内测期要求                                                                                            |
| ------- | ------------------------------------------------------------------------------------------------ |
| 规则模块    | 由部署负责人从只读 `runtime/` 安装 `rules.mjs`，`TURN_RULES_MODULE` 指向容器绝对路径                                 |
| 规则来源    | **必须是 G-03 签署后的正式规则**。合成测试规则、单测规则、示例地点（如样例「青岚镇」）一律不得进内测                                          |
| 未签署时    | 回合与建档返回 `503 RULES_NOT_READY`，这是**正确行为**，不是故障                                                    |
| 叙事岗位    | `story` 必需，其余可选；`NARRATIVE_CONFIG_PATH` 指向宿主 `runtime/narrative.json`；`NARRATIVE_KEY_*` 只在私有环境注入 |
| AI 输出边界 | 只能作为叙事候选与意图提案，不得写入境界、位置、物品、任务或账本                                                                 |
| 日志      | 只含岗位、状态、尝试次数与预算；**不含正文、提示词、密钥**                                                                  |

## 10. 验收与证据

内测环境**自身**的验收（不含玩法/UI 验收）：

- `GET /health` 返回 `status: ok` 且 `saveSchemaVersion` 与 `RC_MANIFEST.json` 一致。
- `GET /ready` 返回 `dependencies.database: ok`。
- `scripts/api-production-smoke.mjs` 通过（不发邮件）。
- 容器日志无密钥、无正文、无提示词（抽样核验）。
- 旧档导入导出在**内测环境**中可用，导出包不含凭据字段。
- 断网 / 刷新 / 关页后原回合可恢复。
- 媒体强制失败时回落静态海报，不黑屏、不阻断回合。
- `/health`、`/ready` 不泄露内部版本以外的部署细节。

**明确不构成内测通过**：CI 绿、容器能起、页面能开。阶段状态以[唯一缺口清单](九霄1.0阶段缺口与人工交接清单-2026-09-29.md)为准。

## 12. 主要失败模式与拒绝条件

出现以下任一情况，**立即停止内测并回退**：

| #    | 失败模式              | 拒绝条件                                                                      |
| ---- | ----------------- | ------------------------------------------------------------------------- |
| F-1  | 规则未签署却开放回合结算      | 出现任何非 G-03 签署规则的结算结果                                                      |

## 13. 1.0 内测非目标

- 不做公测，不做对外发布声明。
- 不做 ICP / 公安 / 算法 / 大模型备案——那是境内公测的前置，不是内测的前置。
- 不做收费、订阅、计量、商户、社区（ADR-0004）。
- 不做媒体生成队列与按需视频。
- 不做原生壳与安装包。
- 不承诺任何帧率、延迟、首屏指标；不把模拟视口当性能证据。
- 不承诺「内测即公测」。内测通过只销账内测自身的验收项。

## 14. 迁移到境内公测环境的触发条件与动作

### 14.1 触发条件（全部满足才启动）

1. G-03 正式规则已由 LYL / Bird 对同一规则版本签署；
2. G-05 四场景媒体权利凭证与文件 SHA-256 齐备，`LICENSE_PENDING` 解除；
3. G-04a 同一 Canon 摘要的双作者独立回执落地，`CANON_RECEIPTS_PENDING` 解除；
4. G-06 运营主体、正式域名、托管地、数据地区、事故联系人、备份策略书面到位；
5. 等保三级与生成式 AI 登记/备案路径已由责任方确认可行。

### 14.2 迁移动作（因 compose 是不变量，代价很低）

1. 采购境内服务器并完成 ICP 备案；
2. 把**同一份** `deployment/api-production.compose.yml` 与**同一个** `API_IMAGE` digest 搬过去；
3. 重跑迁移（幂等，已由 CI 验证两次迁移重复执行）；
4. 重跑 `api-production-smoke.mjs`；
5. **重新定稿出口公网 IP**，并按 G-09 重新申请模型服务商白名单——这是迁移中唯一不可省的动作；
6. 媒体按 G-05 结果决定落境内对象存储还是继续 R2。

### 14.3 迁移中不可做的事

- 不得借迁移之机改 compose、改镜像 digest 或改迁移历史。
- 不得借迁移之机切换到托管数据库或 serverless 运行时。
- 不得把内测期采集的任何数据直接带入生产。
