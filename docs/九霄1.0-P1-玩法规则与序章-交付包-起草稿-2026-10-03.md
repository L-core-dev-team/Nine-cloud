## 一、这份文件是什么，不是什么

**是**：把《P1 玩法规则与序章交付底稿》列出的全部待交付项（`P1-R01`–`P1-R07`、`P1-I`、`P1-E`、`P1-C01`–`P1-C09`、`P1-B`、`P1-H01`–`P1-H07`）**逐项填出可审阅的具体内容**，使 LYL 与 Bird 只需逐条「采纳 / 修改 / 否决」，而不必从空白开始写。

**不是**：

- 不是 LYL 署名的 Canon。底稿第 12 行写明「任何 AI、工程师或测试夹具都不能替 A 创作并签署 Canon」；
- 不是 Bird 的独立回执。采纳裁决第 113 行已声明该裁决文件本身不是 Bird 的回执；
- 不是 P1 验收，也不改变 P0 已关闭的状态。

**因此本稿的处理方式是**：内容全部由我起草并给出具体值，但每一项都标出「应由谁决定」，并保留签署栏。**署名与签署必须由本人完成**——这部分我不代劳，也不建议代劳，因为一旦代签，`FINAL_HUMAN_GATES` 的双签前提就失去意义。

> 换句话说：**我把 90% 的脑力工作做完了，剩下 10% 的「我承认这是我决定的」必须是你自己按下的。**

### P1-R04 交谈

> 这是首段最容易被做成"空转"的一类。底稿第 65 行已预警：交谈和观察可能只有"发生过"而无对象状态变化。

| 字段 | 起草内容 | 决定方 |
| --- | --- | --- |
| 前置 | NPC 在场（`npcPresence[locationId]` 含该 NPC） | A + B |
| 知识边界 | NPC 只能回应**自己获准知道**的内容；不得把传闻说成亲见 | A 明令 |
| 有效判定 | **交谈必须写入 `npcInteractionLog` 才是"完成"**；纯闲聊（未命中主题）也写日志，但标 `outcome=idle` | A 确认 |
| 耗时 | **0 刻**。交谈不推进游戏时间，防止玩家靠刷对话刷时间 | A 确认 |
| 关系变化 | **首段不设好感度数值**。只记 `met: true` 与 `topicLearned[]` | A 确认 |
| 任务线索 | 命中授权主题 → 追加 `clues[]` | A + B |
| 拒绝 | NPC 不在场 / 目标非对话 NPC → 拒绝 | A 裁定 |

> **为什么首段不做好感度。** Canon 里人物关系是叙事核心，但把"好感"做成一个玩家会盯着涨的数值，等于把人物变成刷分目标。首段只留"我们说过话""他知道那件事"两种痕迹——它们是**可被回忆的**，而不是可被优化的。

### 4.2 `clarify` 的结构化扩展（补 `G-12`）

```ts
export const ClarifySchema = z.strictObject({
  status: z.literal('clarify'),
  question: z.string().min(1),                  // 给玩家看的短问
  missingSlots: z.array(z.string().max(8)).default([]),
  candidates: z.array(z.object({
    kind: z.enum(['move','cultivate','acquire_item','use_item','talk','combat','quest','observe']),
    label: z.string().min(1),                   // 人类可读，且可回显为可编辑文本
    slots: z.record(z.string(), z.unknown()),   // 已确定的部分
  })).max(4).default([]),                       // 候选上限 4，顺序按上列固定
  interactionId: z.uuid(),                      // 关联本轮交互
  revision: z.int().nonnegative(),
});
```

- **候选上限 4，顺序固定**（`move → cultivate → acquire_item → use_item → talk → combat → quest → observe`），保证跨设备确定性。
- 候选 ID **只从当前可见集合生成**（`knownLocations`、`npcPresence`、`clues`、`inventory`），不得凭空造。
- 澄清**不产生**世界事件、耗时、状态变更——与底稿第 74 行一致。

### 4.4 冻结输入语料的分层要求

裁决第 46 行要求自建冻结语料、按分层盲标，**不得引用无来源的准确率数字**。分层：

| 层 | 例 | 期望 |
| --- | --- | --- |
| 已知动作 | "走到望气台" | 唯一命中 |
| 缺槽 | "我看看那边" | 缺 `targetId` → 澄清 |
| 多义专名 | "去青芜"（两地同名）/ "找岑九"（人名与地名） | 候选，不猜测 |
| 否定 | "不要去望气台" | **不结算**，不当作移动 |
| 条件句 | "如果天没黑就去望气台" | 未解析条件 → 澄清 |
| 跨轮指代 | "那边" | 需 `interactionId` 上下文，缺则澄清 |
| 未知 | "找老李" | 原文回引确认 |
| 超范围目标 | "去洪荒妖林核心" | 规则拒绝（非解析拒绝） |
| 过时 revision | 旧 `expectedRevision` | `revision-conflict` |
| 重复提交 | 同键同正文 | `duplicate` |

> **门槛写法**：「冻结测试集上**未发现误接受**」，并报告样本量、分层与标注一致性。**不写"总体误解析率为 0"**——有限测试证明不了总体。
