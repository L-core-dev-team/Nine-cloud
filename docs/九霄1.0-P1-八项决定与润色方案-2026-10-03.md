# 第一部分 · 八项决定

## 决定 1 · 全部具体数值

### 1.1 时间制：采用清制 96 刻制

**核实依据（联网，2026-10-03）**

| 制度 | 一昼夜 | 一刻合现代 | 与十二时辰是否整除 |
| --- | --- | --- | --- |
| 百刻制 | 100 刻 | 14.4 分钟 | 否（100÷12≠整数） |
| 96 刻制（**清制正式**） | 96 刻 | **15 分钟** | **是（96÷12 = 8 刻/时辰）** |
| 120 刻制 | 120 刻 | 12 分钟 | 是，但刻度与现代钟表不吻合 |

**决定**：`gameTime` 以**分钟为内部整数单位**；一昼夜 = 1440 分钟 = 96 刻；一刻 = 15 分钟；十二时辰每时辰 8 刻。

**推导**：1440 ÷ 96 = 15，且 96 ÷ 12 = 8。两个方向都整除——这是三种历史制度中唯一同时满足考据与玩家直觉的方案。现代汉语里「一刻钟」默认 15 分钟，界面显示「卯时三刻」玩家不会觉得别扭，而内部 `300 + 3×15 = 345` 分钟可精确回算。

**显示层换算**（B 实现）

```
时辰序号 = floor(gameMinute / 120) mod 12          // 0=子
刻序号   = floor((gameMinute mod 120) / 15)          // 0–7
显示     = 「{子丑寅卯辰巳午未申酉戌亥}[时辰序号]正/初刻[刻序号]」
```

> **为什么用时辰而不是数字**：玩家看到「卯时三刻」就知道天亮了；看到「gameMinute=345」什么也看不出来。`gameMinute` 只进回执，不进 UI。

### 1.2 起点时刻

**决定**：新档 `gameMinute = 300`，即**卯时初刻**（05:00，日出）。

依据：首屏文本写「天刚亮」，卯时正是「日出」之时（《十二时辰》：卯时为日出，05–07 时）。序章文本与系统时间由此对齐，**文本不是装饰，是状态的可视化**。

### 1.3 体力（stamina）公式

**先定性**：体力在《九霄》里**不是可囤积的资源池，而是「日课」额度**。

依据（联网）：游戏体力设计的三条共识——① 上限过高则消耗失去决策意义；② 恢复过慢则等待与核心体验对立；③ **耗尽应是软失败状态而非硬失败**。

**决定**

```
staminaMax            = 100
staminaResetAnchor     = 300   // 卯时初刻（gameMinute）
staminaOnNewDay(v)     = staminaMax - v
                          其中 v = (floor((300 - v) / 1440)) 对齐到最近的一次重置
实现：任意时刻求 n = max(0, ceil((v - 300) / 1440))，
      有效体力 = min(staminaMax, stamina_剩余 + n × staminaMax) - 当日已消耗
简化实现：存档记 staminaCurrent 与 staminaDayIndex；
      读取时若 staminaDayIndex < floor((gameMinute - 300) / 1440) 则整日重置
```

**成本表（全部取 5 的倍数，便于口算与心算）**

| 行动 | 条件 | stamina 消耗 | 备注 |
| --- | --- | --- | --- |
| `move` 正常 | 相邻边 | **5** | 基准单位 |
| `move` 受阻 | 边被落石堵 | **10** | 2× 正常 |
| `move` 绕行 | 礁石小径，多 1 刻 | **15** | 3× 正常 |
| `observe` 环视 | — | **3** | |
| `observe` 细察 | — | **6** | 2× 环视 |
| `cultivate` | **每刻 20** | 20 × minutes | 与耗时线性 |
| `talk` | — | **0** | 交谈不耗时也不耗力，**防止刷对话** |
| `combat` 驱退 | — | **25** | |
| `use_item` | — | **0** | 物品自身已消耗 |

**余量推导**

```
最短通关路径：
  芦花渡环视 3
+ 移动到望气台 5
+ 望气台环视 3
+ 细察落石 6
+ 战斗驱鸦 25
= 42

余量倍数 = 100 / 42 ≈ 2.38
```

**决定**：2.38 倍余量意味着玩家**能失败两次或走两条支路仍不至于卡关**。不足 1.5 倍会让「一次失误就要等一天」成为常态；超过 3 倍则体力沦为装饰。2–2.5 是叙事型游戏的健康区间。

### 1.4 心力（spiritStamina）

```
spiritStaminaMax = 100
combat 消耗      = 25      // 同 stamina 的单次战斗成本
受挫撤退后       = 5       // 见 1.6
```

**决定**：心力**不随日重置**。体力管「今天还能做多少事」，心力管「还剩多少气力」。两者分离的语义：熬一夜可以恢复体力，但气力要靠休息或机缘补——这是修仙世界该有的层次。

### 1.5 修炼进度公式

**决定**

```
cultivationProgressMax = 10000       // 炼体期圆满
cultivate 每刻增益     = 800
有效进度 = min(10000, progress + 800 × minutes)
```

**推导**

```
每日可修炼次数 = floor(100 / 20) = 5 次（每次 1 刻）
每日进度上限   = 5 × 800 = 4000
达成圆满需要   = 10000 / 4000 = 2.5 天（且需连续修炼）
```

**关键判断**：首段玩家实际游玩约 1–2 天，进度落在 **800–4000（8%–40%）**。这意味着：

- 玩家会明确感到「我在变强」；
- 但**离突破还很远**，没有触发突破叙事的风险；
- 突破因此成为**玩家主动宣告的事件**，而不是数值撞线的副产品——这与 Canon「炼体→炼气」的境界描述相容，也把突破的戏剧性留给了正式规则版本。

**强行修炼（合法失败）**

```
条件：stamina < 20 时仍发起 cultivate
结果：进度 +200（¼ 正常），stamina 全额 −20，fatigueCount +1
理由：惩罚以「效率损失」而非「禁止」表达，避免硬拒绝带来的挫败
```

### 1.6 战斗三态判定

**决定：首段战斗不引入随机数**，采用**确定性三态裁决**。

| 态 | 触发 | 结果 |
| --- | --- | --- |
| 驱退 | 玩家 stamina ≥ 25 **且** 持有 `item_bishuifu` 或在渡口作业位 | 鸦群散开；`obstacleState='cleared'` |
| 险胜 | 玩家 stamina ≥ 25 但无上述条件 | 鸦群散开；`spiritStamina` −25 照常；`injuryFlags` +`{'crow_scratch'}` |
| 受挫撤退 | 玩家 stamina < 25 **或** spiritStamina < 25 | `spiritStamina = 5`；退回 `loc_luhuadu`；`injuryFlags` +`{'retreated'}`；任务**未完成**，次日可再来 |

**为什么不用随机**：玩家在第 5 回合就该知道自己会不会赢。三态裁决把胜负交给**准备与判断**，而不是运气——这与「修行有代价，选择有后果」而不惩罚运气差的人是同一件事。

**为什么不是永久死亡**：问卷与裁决都指向「有惩罚但不致命」；且 1.0 的记忆机制尚未实现，死亡会造成不可恢复的状态，这在该阶段不可接受。

### 1.7 物品容量

```
maxSlots = 8
```

**推导**：首段实际涉及 2 件（避水符 + 旧驿符）。给 8 格 = **4 倍余量**。选择 4 而非 10：背包格子一旦超过 8，玩家会开始把获得物品当成收集目标；8 格足够表达「有取舍」而不诱发刷取。

## 决定 2 · 是否允许「认识新地点」写入 `knownLocations`

**决定：允许，但设三条硬限制。**

```
允许：observe 成功产出 clue 且 clue 含 newLocation 标记 → 追加 knownLocations
允许：任务奖励显式解锁边（quest_first_clearance → loc_zheguiping）
禁止：无 clue 依据时任何方式写入
禁止：一次观察解锁 > 1 个地点
禁止：首段总地点数 > 4（芦花渡/望气台/折桂坪 + 1 预留）
```

**理由**：观察若不能改变「世界有多大」，就退化为看风景——这正是 P1-R07 要防的。但开放无限制会让地图在首段就失控，而首段验证不了多地图分支的规则。**4 个地点是「够证明可扩展、又不会被首段玩坏」的上限。**

## 决定 3 · 岑九是否挂 `faction_sihai_shanghui`

**决定：不挂。**

**理由**：
1. Canon 中 `faction_sihai_shanghui` 是**商会**（四海商会），而岑九是**雇工**。把雇工标为势力成员，等于在数据层声明他属于商会编制，与「散修/自雇」的实际身份不符。
2. 后果具体：若他属于商会，玩家与他建立关系会被后续剧情误读为「入会」，产生**未授权的 Canon 推论**——这正是 P1 阶段要杜绝的。
3. 交接表 `P1-H05` 之后若剧情需要他与商会有关系（欠账、同盟、冲突），由 A 补挂并走 Canon 变更流程，**不在 P1 预支**。

**替代记录**：`npc_cenjiu.affiliation = 'unaffiliated'`，并在人物卡写明「受雇于芦花渡渡口分舵，按趟结算」——信息保留，但不进结构化归属。

## 决定 4 · 是否需要第二个 NPC

**决定：不设。**

**理由**：
1. 首段的验证目标是**规则闭环**，不是社会规模。一个引路人已足够暴露全部六类行动。
2. 第二个 NPC 会立刻引入「同一事件授权给谁、谁没被授权」的对照问题，而**授权观察 outbox 属于 P2/P4**（采纳裁决列为最高工程优先级，尚未实现）。在没有授权机制时放两个 NPC，等于让 B 无法判断记忆行为是否正确。
3. 双 NPC 授权样例应在 **P2/P4** 作为 outbox 验收用例补上，而不是在 P1 用真实 Canon 承担。

**保留**：首段留一个**不参与任何授权判定**的功能性对象——渡船（`obj_ferry`），用于承载「船没坏，水浅了」这条线索的物证，让线索有来源而非凭空出现。

## 决定 5 · `observe` 是否独立 ActionIntent kind

**决定：独立 kind。**（采纳裁决已把它列为候选，此处拍板。）

```ts
z.strictObject({
  kind: z.literal('observe'),
  payload: z.strictObject({
    targetId: z.string().min(1),
    method: z.enum(['scan', 'study']),   // 环视 / 细察
  }),
})
```

**三条理由**：
1. **语义不可合并**：与 `talk` 合并会把「观察是否改变关系」污染进交谈规则（首段交谈明确不产生关系数值）。
2. **不走 `free_text`**：并入 `free_text` 正是 P1-I 要防的绕过路径。
3. **成本可分辨**：`scan` 与 `study` 的耗时与 stamina 成本不同（3/6），合并后无法表达「看得更仔细要更费力」。

**与采纳裁决的一致性**：其第 84 行要求「不得先加一个只有叙述、没有规则语义的动作」——本决定已为 `observe` 配齐目标、成本、成功/无发现/受阻三态与可核对字段，满足该前置。

**新增契约字段**：`targetId` 允许引用 `npc / location / obstacle / prop` 四类目标，`method` 决定扫描半径与线索粒度。

## 决定 6 · `branchId` 是否升为 1.0 运行契约前提

**决定：不升为 1.0 前提，但在 schema 中预留。**

**理由**：
1. 采纳裁决第 114 行要求先做产品决定——**这就是该决定的答案**：1.0 没有分支、跨模式迁移与回滚的产品需求。
2. 若此时把 `branchId` 升为阻断级，会触发全量迁移，而它当下没有任何消费方——**为无消费方字段付出迁移成本是最典型的过早抽象**。
3. 但**必须预留**：`turn_events` 增加可空的 `branch_id` 列，恒写入 `'root'`。这样 P2/P4 引入分支时只需回填历史，不必重写迁移历史。

```
SAVE_SCHEMA_VERSION = 2  时：
  SaveEnvelope.branchId : z.string().min(1).default('root')   // 运行契约不依赖它
  DomainEvent.branchId  : z.string().min(1)                    // 恒为 'root'
  ActionIntent.branchId : z.string().min(1).default('root')
规则：1.0 运行期不提供创建分支、跨模式迁移、回滚的 UI 入口。
```

## 决定 7 · 序章文本字数与朗读时长

**决定**

| 段 | 字数 | 朗读 |
| --- | --- | --- |
| 首屏 | ≤ 60 字 | ≤ 20 秒 |
| 单次观察结果 | ≤ 80 字 | ≤ 25 秒 |
| 单条 NPC 台词 | ≤ 20 字 | ≤ 7 秒 |
| 成功/失败/受挫文本 | ≤ 40 字 | ≤ 14 秒 |
| **首段文本总量** | **180–260 字** | **≤ 90 秒** |

**推导**：`FINAL_HUMAN_GATES` G-05 与 `S5 真实手机验收模板` 要求真机连玩 ≥15 分钟。首段文本若超过 260 字，按普通阅读速度 250 字/分计需 62 秒纯阅读；控制在此范围内，才能保证 15 分钟里**动作与尝试**占主体而非**阅读**。

**朗读校验**：B 端可用 TTS 时长反推字数；不可用时按 240 字/分折算并留 15% 余量。

## 决定 8 · 云端配额是否适用于首段

**决定：不适用。** 首段全在本地，**不产生任何云端写入**，因此不触发 `CLOUD_QUOTA_EXCEEDED`。

**理由**：
1. 配额门禁挂在 `PolicyCloudSaveRepository` 上，仅对已登录玩家的云档写入生效。
2. 首段要求「无密钥、无账号可完成」，因此游客路径**根本不会进入该仓库**。
3. 首段唯一可能产生云端交互的是**已登录玩家主动开启同步**——那是 S6 行为，受 P1 之外的政策门禁约束。

**在 1.0 阶段的实际影响**：
- 游客：完全本地，无配额概念。
- 已登录玩家：只有手动提交云档才占用配额；配额超额时**拒绝上传但保留本地档**，不阻断游戏。
- 建议 UI 文案：「云端满了，本地存档不受影响」——避免玩家以为进度会丢。
