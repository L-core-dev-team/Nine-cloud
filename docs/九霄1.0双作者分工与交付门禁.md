# 《九霄》1.0 双作者分工与交付门禁

> 版本：2026-09-23。性质：两位作者的责任、交接与发布约定；不是已完成事项清单。
> 目标依据：[1.0 公测版重建总方案](九霄1.0公测版重建总方案.md)；体验依据：[11 项建议落实方案](九霄1.0产品体验与11项建议落实方案.md)；代码阶段见[AI 执行清单](九霄1.0分阶段实施与AI执行清单.md)。
> 与旧文件关系：`九霄双人并行实施方案.md`、`合作者执行方案.md`、`技术联合负责人执行方案.md` 记录长期七阶段和 0 号试玩安排；本文件专门规定新的“全功能成熟后公开”的 1.0 交付，不把旧四周/十二周建议当作 1.0 截止日期。

## 1. 两位作者的权威边界

**作者 A：项目发起者、产品主理人、Canon 与体验负责人。** 主导九霄为何存在、玩家体验、人物、世界设定、剧情骨架、审美方向、内容冲突裁决，以及功能是否真像九霄。A 对玩家可见的 Canon 和产品验收负责。A 不能凭体验判断绕过存档、安全、账务或权威事件契约。

**作者 B：技术联合负责人、规则契约、工程与证据负责人。** 主导 Web/API/数据/安全架构、ActionIntent 与 DomainEvent、AI 调度、构建部署、性能、迁移、故障恢复、运维与工程验收。B 对技术可复现性负责。B 不能未经 A 审核改写 Canon、人物动机、付费价值陈述或叙事语气。

没有第三位常驻开发者作为默认前提。法律、游戏运营、支付和会计的专业核定可由合适的外部专业人员完成；其结论是发布输入，不等于把两作者的产品或工程责任转移出去。缺席的专业结论不得由模型猜测补齐。

## 2. 决策权与否决边界

| 决策事项 | 定案人 | 必须参加审查者 | 形成的证据 | 阻断条件 |
| --- | --- | --- | --- | --- |
| 产品宗旨、目标玩家、1.0 体验与功能优先级 | A | B | 产品规格、任务脚本、非目标 | 与已签署的公测完整性要求冲突 |
| Canon、人物、九境五域、剧情骨架、OCR 冲突 | A | B 核对数据影响 | 原图/文本来源、裁定记录、版本 | 无原图或来源不足仍拟公开 |
| 玩法规则语义、失败条件与结果合理性 | A 定义意义，B 定义可执行契约 | 双方 | 规则表、例子、反例、测试 | AI 可越过规则改事实 |
| ActionIntent、DomainEvent、状态投影和接口 | B | A 检查玩法表达 | ADR、schema、契约测试 | 不能回放、不能幂等或与 Canon 冲突 |
| UI 风格、叙事节奏和玩家任务 | A | B 核对可用性/性能 | 原型、真机任务记录 | 首屏迷路、长文难读或性能不达标 |
| 存档迁移、账户、同步、隐私和安全 | B | A 检查玩家影响与文案 | 样本、恢复演练、威胁模型 | 丢档、越权、泄密或无回退 |
| 云订阅、模型额度、1% 网关费率与价格表 | A 决定产品和价格，B 验证成本及技术实现 | 双方 | 签署价格表、单元经济表、对账样本 | 单位经济为负却未重新批准，或无法核对成本 |
| 公测发布与撤回 | A 与 B 双签 | 双方 | 发布记录、版本/制品哈希、验收报告 | 任一方对其权威范围给出阻断结论 |

安全、隐私、账务、存档损坏、Canon 越权和核心任务失败属于硬门槛。即使 A 认可体验，B 可据可复现的工程证据阻断；即使 B 证明系统稳定，A 可据来源和试玩证据阻断。争议写成 ADR：问题、各方依据、影响范围、可逆性、候选方案、裁决及复审条件。未达一致时状态为“阻断”，不得以沉默视作同意。

## 3. 文件与 PR 的主责

A 主责产品规格、玩家任务、世界书审定、人物/剧情、视觉与声音选择、文案、内容验收记录。B 主责应用代码、共享规则、API、数据库迁移、测试、构建/部署、性能/安全报告。生成 HTML、媒体转码和发行包只由流水线生产，不手工改发布物。两人共同维护本组三份方案及发布决定，任何实质变更须双审。

实施后建议的 GitHub 所有权按职责设置：内容与 Canon 目录由 A 主要审查；domain、API、数据库、安全和 CI 由 B 主要审查；路由、UI、交互与发布文件由双方审查。主线应开启 PR 审查、必过检查与禁止直接推送。当前 `main` 是否已经保护须以 GitHub 设置实时核实；文档不把拟议规则写成已生效事实。

内容 PR 不直接改规则代码；技术 PR 不擅改 Canon。跨边界工作拆成有关联的两个 PR，先冻结契约和验收样例，再分别合入。仅有两位作者时，每个 PR 至少有非提交者的实质审查；涉及双权威的改动附双方明确结论。对私有 OCR、原图、密钥和玩家记录设置单独访问范围，禁止为方便评审而推到公开仓库。

## 4. 五个关口各自交什么

| 关口 | A 的交付与签字 | B 的交付与签字 | 联合通过证据 |
| --- | --- | --- | --- |
| G0 旧版证据冻结 | 旧版能力清单、玩家任务脚本、首批 Canon 与原图接收清单、四场景体验标准 | 旧版/现版哈希、存档样本、代码与构建基线、GitHub 主线及 CI 状态 | “旧能力—新位置—验收动作”逐项可执行；OCR 私有边界已标明 |
| G1 导航与迁移 | 首页、建角、世界、游戏、青鱼设置的文案与原型；两作者现场走任务 | 路由、旧字段和 AI 功能迁移、唯一构建、旧档原样备份与导入 | 陌生玩家首屏不迷路；旧能力没有静默丢失；同一制品回归通过 |
| G2 世界与游戏 | 九境五域规则表、剧情禁则、182 份逐图裁定、NPC 认知样例、四场景资产选择 | 规则/事件引擎、记忆隔离、叙事重试、内容版本、媒体编排与运行测试 | 长线代表路径、Canon 来源、回合回放和四场景真机表现通过 |
| G3 在线产品 | 社区审核准则、隐私/费用文案、订阅与额度价值说明、最终价格表 | 账户、云同步、网关、社区队列、计量账本、支付/退款、安全与运维 | 两账号隔离、冲突恢复、敏感数据处理与账务对账通过 |
| G4 公测封版 | 100 回合盲评、真实玩家任务、视觉声音与社区体验签字 | 真机性能、故障/恢复、备份、制品哈希与部署回退签字 | 外部法务/商户条件齐备；双签后才公开 |

G0 至 G3 可在私有环境预览，不对公众开放删减版。任何关口失败退回相应 Issue；失败记录不能从报告里删除。A 和 B 可以并行准备下一关的材料，但不能让未过关内容进入公开构建。

## 5. 错峰协作：每个 Sprint 的固定交接

A 在 Sprint N+1 提供产品输入；B 在 Sprint N 实现已冻结规格；A 同时验收 Sprint N 的产物。B 提前标记 N+1 的技术风险和证据缺口。每轮控制在可复现的一组玩家任务，不以“整套世界已做完”作为一个不可审查的 PR。

**A 的输入达到 Ready，至少包含：**

- 玩家为什么需要该能力、从哪里进入、完成后看到什么。
- 涉及的 Canon 来源、人物/地点 ID、禁则与未知项；未知项保持待核。
- 正常、失败、取消、断网/无模型四类任务脚本及期望结果。
- 视觉或音频参考及许可状态；不得仅写“更电影级”。
- 对旧档、现有内容和付费文案的影响。

**B 的实现达到 Ready，至少包含：**

- 计划改动的路由、契约、数据迁移和回退方式。
- 权威事件与叙事/记忆/媒体的写入边界。
- 安全、隐私、计费、性能和跨端风险。
- 可复现测试、需要的原图/商户/账号等外部输入。
- 若采用第三方技术，基准、替代方案、版本和许可。

缺少关键 Canon 来源时，B 可实现与内容无关的接口，但不能补写权威设定。缺少可执行失败条件时，A 须补规格，B 不靠提示词“猜测裁判”。交接以 Issue/PR/ADR 留痕，不以聊天里的“应该可以”代替审定。

## 6. 每类成果的完成定义

**产品与内容完成：** 来源清楚，冲突已裁定，玩家入口可找到，A 用真机任务脚本亲自完成；旧能力对照和版本影响已记录。182 份 OCR 逐图审定是独立门槛，不能把“有 OCR JSON”计为完成。

**规则与工程完成：** 同一版本的代码、契约、数据库迁移、自动测试和制品一致；正常、失败、重试、断网、并发、回滚都已运行；B 能用记录重现结论。模型文本、NPC 遗忘或插件输出不能直接提交世界事实。

**视觉与声音完成：** 四场景的静态与动态表现、移动裁切、静音/弱动效/省流量回退、来源许可和目标设备性能均过关。A 审美签字与 B 性能签字缺一不可。

**商业与社区完成：** A 签署用户可理解的权益、价格和审核政策；B 验证身份、计量、支付、退款、对象鉴权、日志脱敏、删除与恢复。外部运营条件仍缺时，只能标为“内部功能验收通过，公开发布阻断”。

**公测完成：** G0–G4 全过，版本号和制品哈希固定，两位作者签署同一发布记录；有回滚包、值守和事故联系人。PR 可合并不等于已部署，部署成功也不等于已通过产品验收。

## 7. 具体故障与争议如何处理

- **旧版入口再度隐藏：** A 提供首次玩家录屏及失败动作；B 定位路由/布局根因；修复后同一脚本在手机与桌面复测。
- **OCR 与剧情冲突：** A 查看原图并裁定；B 更新 Canon 版本和旧档解释。原图未到时条目保持待核，不让模型裁决。
- **叙事写出不存在的物品或复活死者：** B 判定事件/投影是否被越权；A 判定人物与文本损伤。先保证状态不变，再调整提示、过滤或规则。
- **1% 网关亏损：** B 提供供应商账单、支付手续费及请求成本核算；A 决定是否更改产品价格。未共同批准前停止收费上线。
- **性能与电影感冲突：** A 指出必须保留的剧情线索；B 给出不同设备的帧率、包体和回退证据。优先保留可读的线索，降阶表现而非阻断任务。
- **发布前意见不一致：** 任一方在发布记录写“阻断”、证据与解除条件。不得以另一方忙碌或沉默替代签字。

## 8. GitHub 与发布记录模板

每个 Issue 写清：用户任务、现状证据、目标行为、范围外、主责人、审查人、依赖、风险、可复现验收。PR 描述附：关联 Issue、旧功能影响、数据/Canon 版本、截图或录屏、自动测试、真机结果、回退方式、外部未满足条件。评审意见区分“阻断”“建议”“需要 A/B 裁决”。

发布记录至少写：版本与提交 SHA、构建制品 SHA-256、数据库迁移号、Canon 版本、规则版本、旧档迁移样本、四场景资源清单、性能/安全/支付/社区报告链接、未解决问题、回退负责人、A 和 B 的明确结论。仅这份双签记录可以把状态从“内部候选”改为“公开公测”。

公开后，B 负责监控可用性、错误率、存档和账务异常；A 负责玩家任务、内容与社区反馈。事故先保全存档和账本，再评估视觉或叙事修复。重大 Canon 或存档更正仍走版本化 PR，不直接改线上数据库中的历史事件。

## 9. 时间与资源的诚实边界

本版范围跨越长期七阶段的多项能力，但核心作者只有两人，且原图和运营主体尚未到位。不能对外承诺固定发布日期，也不能用多开任务或大量 AI 生成文字替代逐图审定、真实长局、支付和真机验证。每周报告只列已跑通的玩家任务、未通过门槛、下一步输入和可复现证据。是否需要外部美术、音频、法务或测试资源，由两位作者依据具体缺口共同决定；未落实前保持相应发布阻断。
