# S6 认证后端闭环与前端接口交接

本轮仅修认证后端和必要的错误响应兼容。Cloudflare Pages 构建、部署、页面登录交互与 API Base URL 注入由另一个任务负责；未修改其构建与部署文件。`apps/web/src/cloud-sync.ts` 仅保留服务器错误码、阶段、requestId 的兼容读取，不新增部署逻辑。

## 故障定位与当前边界

- 当前本机 `localhost:4173` 无运行服务，不能复现用户那一次实机请求。
- 未开启认证的 API 对 `/api/auth/code` 返回 404，邮件发送根本未执行；这是可复现路径，不代表实机一定是同一原因。
- 本地没有已配置的 `.env`；GitHub 仓库 deployments/environments 查询没有返回可确认的公网 Auth API 部署。未获得真实 SMTP/数据库部署配置。
- 服务端现在区分 `VERIFICATION_STORE_FAILED`、`MAIL_AUTH_FAILED`、`MAIL_UNAVAILABLE`、`MAIL_REJECTED`，503 响应含脱敏 stage/requestId，不含服务商原始报错或凭据。
- 成功仅表示 SMTP 已接受目标收件人；不宣称实际到达收件箱。失败会失效化已签发验证码，数据库写入失败不调用 SMTP。

## 正式 API Base URL 合同

**已部署、可用的公开 HTTPS API Base URL：尚未提供，`PUBLIC_API_BASE_URL_PENDING`。** 不能把示例域名写成已上线地址。

后端最终需提供一个实际的 `https://<认证后端公网域名>`（不含 `/api`）。前端任务应把这个值配置为公开的 API Base URL；请求路径如下：

| 方法 | 路径 | 输入 / 输出 |
|---|---|---|
| POST | `/api/auth/code` | `{email}` → 202 `{status:"sent",resendAfterSeconds:60,expiresInSeconds:600}`；限流 429 + Retry-After |
| POST | `/api/auth/verify` | `{email,code}` → account + HttpOnly Cookie；错误/过期/已用 401 |
| GET | `/api/auth/session` | 当前 account；无会话 401 |
| POST | `/api/auth/refresh` | 刷新会话，旧 token 失效 |
| POST | `/api/auth/logout` | 撤销会话、清除 Cookie |
| GET | `/api/save-index` | Cookie 鉴权，返回当前用户云档 |

前端正式请求必须使用实际 HTTPS API Base URL + 路径，跨域 fetch 必须 `credentials: 'include'`；现有 `same-origin` 请求选项不足以访问独立 API 域名。此接入由前端任务实现，未在本轮重构。API 精确允许 `AUTH_PUBLIC_ORIGIN`，不使用 `*`，预检只允许已有方法和 Content-Type / X-Jiuxiao-Account。

建议前端与 API 使用同一注册域名下的 HTTPS 自定义域名，保留 `AUTH_COOKIE_SAME_SITE=Strict`。若 Pages 域名与 API 完全跨站，需要显式 `AUTH_COOKIE_SAME_SITE=None`，只允许 HTTPS；iPhone Safari 的第三方 Cookie 策略仍可能阻止会话，此时应由部署任务配置同站自定义域名或同源 `/api` 代理，不能绕过浏览器安全设置。真实 iPhone 验收待做。

## 服务端配置与验证顺序

仅配置在后端私有环境：

- Node 24、PostgreSQL、已执行 `pnpm --filter @jiuxiao/db db:migrate` 的数据库。
- `DATABASE_URL`、`AUTH_ENABLED=true`、随机至少 32 字节的 `AUTH_SECRET`。
- `AUTH_PUBLIC_ORIGIN`：前端真实 HTTPS origin，不能有路径或末尾斜线；不是 API 地址。
- `AUTH_MAIL_FROM`：邮件 Provider 已授权发件地址；`SMTP_URL`：587 用 smtp://，465 用 smtps://，账号密码须 URL 编码。
- `AUTH_COOKIE_SAME_SITE=Strict`（同站默认）或经验证的 None。
- 容器监听需按宿主配置 `API_HOST`、`API_PORT`，公网反向代理提供 HTTPS。
- `AUTH_MAIL_PREFLIGHT=true` 可启用启动连接检查；连接成功不等于真实投递成功。

已有部署基础继续复用 `apps/api/Dockerfile`；本轮不创建收费资源，不切换邮件 Provider。根目录 `.env` 不自动被 API 加载：本地使用 `node --env-file=.env apps/api/dist/index.js`，生产平台通过私有环境变量注入。

构建后运行 `node --env-file=.env scripts/verify-auth-mail.mjs`，只检查 SMTP DNS/TCP/TLS/AUTH，不发送邮件、不输出凭据。接着用真实邮箱发一次验证码，检查实际收件箱/垃圾箱，再验证、查询 session、读取与上传本人云档，注销后确认 401；用第二账号验证无法读取第一账号的云档。只留下脱敏状态、requestId、commit/build 和结果，不留验证码/密码/token。
