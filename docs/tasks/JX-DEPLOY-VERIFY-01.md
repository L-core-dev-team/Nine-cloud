## 三、只读核对生产，保护现有数据

复用执行端已经具备的主机、部署平台和数据库只读访问。只收集本任务需要的版本信息；不得将完整环境变量、密钥、Cookie、连接口令或真实玩家正文写入报告。

如使用容器，记录实际服务容器与镜像 digest，核对 revision 标签和部署记录。没有标签时按构建记录追溯，不能凭镜像名称或创建日期猜 commit。

数据库用只读事务核对：

1. 人物资料字段是否存在、类型是否符合实际 API；
2. 迁移记录表实际所在 schema、已应用记录及与源 SQL 的对应关系；
3. 是否存在“前端会发送、后端不读写”或“后端依赖、数据库尚未具备”的字段。

字段存在不等于完整迁移链已核对；health 正常也不能替代资料持久化验证。不要通过执行迁移、升级镜像或改生产配置来消除版本差异。

若没有主机／数据库访问，明确写出缺少哪一项可验证信息。继续完成公开入口、源码和可重建环境的部分，不要求用户把凭据发到聊天。

## 四、在对应的隔离组合里验证保存

先证明隔离环境对应哪套实际运行组合，再验证行为。若无法重建生产组合，所得结果只能标为候选验证，不能代替生产兼容性结论。

使用合成账号和有辨识度的测试资料，按实际字段填写。通过正式页面或同一提交构建的页面走真实接口，不用模拟建档回包代替服务端保存。

最小完整路径：

1. 建立角色并提交资料，记录请求键、响应、存档 ID 与修订。
2. 从服务端独立重读，逐字段核对填写值和默认值；不能只看浏览器显示。
3. 刷新后读取；停止并重启隔离 API 后读取；用新浏览器会话重新登录测试账号后读取。
4. 对同一建档请求正常重放，确认没有第二份存档或重复副作用；沿用已有冲突契约检查同键异参。
5. 用另一测试账号访问该存档，确认不能读到资料。
6. 验证已有存档缺少新增可选资料时仍可正常读取，不被新字段要求挡住。

优先复用既有建档、权限和恢复用例，只增加本次运行组合缺少的验证。使用模拟模型或免费正文，不输入供应商 Key。
