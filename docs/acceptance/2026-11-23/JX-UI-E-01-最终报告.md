# JX-UI-E-01 最终报告

**结论：UI-E-01 PARTIAL**

第一轮（上午）落地了视觉体系和主要页面；第二轮（下午，道主授权“能做的接着做”）补上了第一轮缺的四个页面、可编辑设计源文件和真实流程录屏：

- P04 人物志：卡片详情改为“列传”抽屉；会话建立后落印入卷；
- P08-b 世界书三栏工作台；
- P09 “两套 AI 互不通用”说明区；
- P12 只读成卷模式（横排书页 / 竖排手卷，构建开关后，默认关闭）；
- 入卷转场与纸纹；
- Figma 设计源文件（变量 + 三页样张）；
- 本地合成模型下的角色卡完整流程录屏，桌面与手机各一段，录屏中发现并修复一个显示名缺陷。

第三轮（2026-11-24，道主授权：境界铭牌由我决定、M5 补完、零费用的缩略图接口、体验与性能、部署到正式站）：

- **M5 补完**：存档管理改为“命牌”；账号与云档页重排；画面设置改为“四扇屏风”，用木框保证控件边界清楚；
- **境界铭牌**：数据只取规则写入的修为，不由界面推算。铭牌是一枚玉璧，璧环就是修为进度；点开是“九重天”境界图，引用 Canon《修炼境界介绍》。云端游玩和本机 1.0 预览玩法都有；
- **卡库缩略图接口**：在现有 Node 宿主和 PostgreSQL 上实现，不新增任何付费服务；
- **体验与性能**：切换主题不再重建 WebGL；云端游玩页和内部回合工作台改为按需加载；
- **已部署到正式站** <https://play.jiuxiaogame.cn/>（2026-11-24 12:34 UTC，部署 `e617890e`），记录见第 11 节。

仍未完成、所以结论仍是 PARTIAL 的部分：

- 屏幕阅读器和实体设备还没有实测。正式站上线后已能测，步骤见[核对清单](JX-UI-E-01-读屏与真机核对清单.md)；
- 手机 LCP（慢速 4G 模拟约 4.2 秒）仍未达 2.5 秒目标，基线同样未达；
- 缩略图接口已写好，但正式站的 API 服务器不在本次部署范围内；角色卡模式在正式站也未开放，所以线上还用不到它。

## 3. 视觉与设计系统

- **分层**：8 个旧样式文件放入 `@layer jx.legacy`，新设计在更高的层。等值验证：40 组整页截图逐像素比较，差异为 0。
- **Token**：`tokens-v2.css` 定义原始色阶与语义 Token，三层（`data-jx-layer`）× 两主题；新增控件边线色 `--jx-line-control`，按 WCAG 1.4.11 要求 ≥3:1，有自动测试。
- **字体**：自托管思源宋体 400/600（`@fontsource/noto-serif-sc` 5.3.1，OFL-1.1，许可证随包分发，已登记许可证审查）；woff2 按字符切片；字体声明表在首屏后空闲时加载，不阻塞渲染。
- **签名元素**：浑天环（SVG）、月洞门、朱印（文字由 CSS 绘制，不进入可访问名）、矿彩首字占位；`/__design` 开发样板集中展示，生产构建中不包含，并由守卫测试证明。
- **第二轮新增**：
  - 入卷：从灵境进入书阁时，背后场景约 0.9 秒压暗、退远，正文像挂轴自上而下展开一次（遮罩只在动画期间存在）；
  - 纸纹：宣纸 / 夜笺纤维（SVG 噪点 + 横向长纤维，透明度 3%–7%），随正文一起滚动，用在阅读纸面、世界设定条目、人物志与成卷；
  - 古籍排版的“格”成为 Token（`--jx-reading-ge-1…4`），朱批、题签、成卷标点都按字宽计；
  - 新增 4 个样式文件全部进入 Token 审计（17 个文件、约 5,760 条声明，0 违规）。
- **第三轮 · 境界铭牌**：
  - 数据：只读规则写入的存档。服务端是 `prologue-v1`，本机 1.0 预览玩法是同一个 reducer、同一组已签字数值，只是内容绑定还是候选（`prologue-v1-candidate-*`）。依作者签字的 P1-R02，角色以炼体期起始，`cultivationProgress` 满 10000 为“炼体期圆满”；首段不开放突破，界面也不推断突破阈值。其他规则版本、本机叙事存档和旧档都不显示铭牌；
  - 形制：玉璧，取“苍璧礼天”。璧环十二刻（周天），金线沿环走到当前修为，璧心是境界的一个字（“体”）；圆满时璧缘转金。修为增加时金光沿环走一周、璧身微亮，读屏同时播报“修为增加 800，现为 N%”；减弱动画时只更新数值；
  - 境界图“九重天”：九境自下而上，越往上越淡；当前境界加粗并压金线。右侧是大璧、数值、按签字规则写的修炼说明，以及 Canon《修炼境界介绍》对应段落和出处；
  - 位置：云端游玩页顶栏；本机 1.0 预览玩法“人物与任务状态”的标题右侧。
- **与原方案的偏离**（为保住既有测试契约而做的取舍）：
  - 首页主按钮保留“进入世界”文案与玻璃材质；
  - 案头层不是纯色，保留约 8% 的场景影子；
  - 世界设定分类保留成组的玻璃托盘。

  详见[锚点变更记录](../../design/JX-UI-E-01/锚点变更记录.md)。

## 6. 性能（实验室测量，不是真实用户数据）

条件：生产构建由本机静态服务器提供，接口离线（503）；Playwright 1.63 Chromium，headless。

- 桌面档：1440×900，不节流。
- 手机档：390×844，CPU 降速 4 倍，网络为慢速 4G 模拟（1.6 Mbps、150ms）。
- 每项 5 次取中位数。
- INP 为页面加载后“切换主题”两次点击的最长事件时长，只是近似值。

| 档位 · 页面 | LCP（ms）基线 → 新 | CLS 基线 → 新 | INP（ms）基线 → 新 |
|---|---|---|---|
| 桌面 · 首页 | 536 → 540 | 0 → 0.009 | 480 → 392 |
| 桌面 · 大厅 | 232 → 600 | 0 → 0 | 352 → 360 |
| 桌面 · 世界设定 | 432 → 408 | **0.17 → 0.032** | 384 → 360 |
| 手机 · 首页 | 6660 → 4496 | 0 → 0.02 | 272 → 296 |

与目标对比：

第二轮的性能尝试（同一测量条件，只测首页与大厅）：

| 尝试 | 结果 | 处理 |
|---|---|---|
| 在 `index.html` 里预加载首屏海报（`fetchpriority=high`） | 手机 LCP 反而变差：首页 4496 → 5688 ms，大厅 4384 → 5568 ms。慢速 4G 下海报与首屏脚本抢带宽，React 渲染推迟 | 撤回 |
| 海报 `<img>` 自身设 `fetchpriority=high` | 只影响脚本执行后的资源排序，没有副作用 | 保留 |
| 卡库缩略图直接按 360px 宽解码（`createImageBitmap` 的 `resizeWidth`，不支持时回退） | 少一次全尺寸解码，内存峰值更低 | 保留 |

第三轮（同一条件，生产构建，中位数）：

| 档位 · 页面 | LCP（ms）第二轮 → 第三轮 | INP（ms）第二轮 → 第三轮 |
|---|---|---|
| 桌面 · 首页 | 540 → 564 | 392 → 约 430（波动大） |
| 桌面 · 大厅 | 600 → 528 | 360 → 272 |

| 手机 · 大厅 | 4384 → 4156 | 224 → 168 |

做了什么：

- 切换主题时，场景层只按新配色重画一帧，不再销毁并重建 WebGL 上下文；
- 云端游玩页与内部回合工作台改为路由懒加载，主包 544 → 476 kB（gzip 约 165 → 148 kB，测试构建口径）；
- 缩略图交给服务端（若可用），卡库首屏少解码整张原图。

手机 LCP 仍高于 2.5 秒，主要成本仍是场景海报，见下一段。

真正的手机 LCP 解法是更小的移动端海报（或 AVIF）。海报登记在素材清单里（含哈希与来源），重新编码要同步更新素材登记并请道主确认画质，所以这一轮没有动。主题切换的 INP 如果改成“先回应点击、下一帧再换主题”，`foundation` 里“点击后立即读取颜色”的断言会变得时序不稳，也没有动。

## 9. 停止线与授权事项

第三轮道主授权：境界铭牌“全部由你来决定”；缩略图接口“不会产生费用就用最好的方法完成”；“将修改后的网站重新部署上去”。

- **卡库缩略图接口：已完成，零新增费用。** 更正第二轮的判断：角色卡导入跑在 Node 宿主（`apps/api/src/card-import/host.ts`）加 PostgreSQL 上，不在 Workers 包里（`src/worker.ts` 不引用它），所以没有 Workers 的 CPU 限制，也不需要新的存储。实现：
  - `GET /api/card-import/imports/:id/thumbnail`，先经原有属主校验读取导入记录；
  - 纯 JS 编解码（`pngjs` 解码、面积平均缩到 360px 宽、透明处合成到卡库底色、`jpeg-js` 质量 82 编码），在一条工作线程里执行，不阻塞 API 事件循环（实测渲染 392 ms，主线程最大延迟 5 ms）；
  - 超过 4096×4096 像素直接拒绝；排队上限 16，超出返回 503；
  - 进程内按“版本 + sha256”做 8 MiB LRU；浏览器 `private, max-age=31536000, immutable` 加 ETag/304；
  - JSON 卡返回 `404 THUMBNAIL_UNAVAILABLE`，前端据此改用首字占位；其他错误时前端退回本地解码。
- **境界铭牌：已完成**，设计与数据来源见第 3 节。
- **部署：已完成**，见第 11 节。

第二轮的记录（保留原文，以便对照）：

- **卡库缩略图后端接口：评估后没有做。** 接口跑在 Cloudflare Workers 上，要在服务端解码最大 8 MiB 的 PNG、缩放并编码，就得引入 WebAssembly 图像库，并受 Workers 单次请求 CPU 时间限制；缩略图还要有地方存（R2 / KV / 数据库），而 Cloudflare Images 等托管方案会产生费用，任务书要求费用另行授权。现有前端方案（只为进入视口的卡读原文件、内存缩略、并发 2、≤2 MiB、LRU 40）已经可用，这一轮又改成按目标宽度解码。如果卡库规模变大到流量成为问题，再按“上传时生成缩略图并存储”单独立项。
- **境界铭牌：没有做，需要作者裁定。** 现状：`packages/domain` 与 `packages/contracts` 里没有任何“当前境界”规则；建角表单的“修为”取自 `REALM_ORDER`，代码注释写明“可编辑的写作建议，不是权威授予”。做成铭牌之前需要作者定下：起始境界怎么定、什么事件让境界变化、由规则引擎还是叙事模型写入、旧存档如何迁移。这些属于游戏规则与 Canon，不应由界面代为决定。授权已记录，等作者给出规则后可以接着做。
- 没有改动认证、存档格式、数据库结构与 Canon 内容；红线目录除第三轮授权的 `apps/api` 缩略图外，相对 #119 仍为零改动。
- 没有调用真实 AI（录屏用 `pnpm dev:cards` 默认的合成模型），没有产生费用（Figma 只用了免费的文件与变量能力，未用付费的图像生成；部署用的是已有的 Cloudflare Pages 项目），没有合并 `main`。第三轮按授权部署了正式站前端。
