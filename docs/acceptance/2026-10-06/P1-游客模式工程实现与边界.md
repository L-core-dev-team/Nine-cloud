## 已作决定

### G1–G6

| 项 | 决定 | 依据与限制 |
|---|---|---|
| G1 会话期限 | 7 天，与邮箱会话一致；显式刷新会轮换令牌并延长 7 天。 | 期限由 `SESSION_SECONDS` 统一控制。玩家须在期限内刷新或升级邮箱。失效或丢失的游客令牌不能凭存档 ID 恢复。 |
| G2 云同步 | 允许。游客与邮箱账号共用 `auth_accounts.id` 与存档所有权检查。 | 账号 ID 和存档 ID 不是凭据。随机 32 字节令牌只以 SHA-256 摘要存储，浏览器 cookie 为 HttpOnly；但会话 cookie 本身仍是 bearer 凭据，泄露或清除后分别带来接管或失去访问风险。邮箱升级用于长期找回。 |
| G3 清除本地数据 | 本地存档和游客 cookie 属于浏览器站点数据。清除站点数据会失去游客云档访问凭据，不会即时删除服务器云档。 | 在线游客资料在连续 90 天无有效访问后进入清理候选范围。到期删除还要求数据政策校验、`ACCOUNT_DELETE_ENABLED=true` 及运营方执行到期任务；目前未核实生产调度器或备份删除状态。 |
| G4 导出/导入 | 支持逐份存档导出。可通过现有本地 JSON 导入，再明确上传为云档。 | 不为游客开放邮箱账号生命周期所依赖的聚合账号导出端点。导入数据先按本地不可信存档处理，不会直接成为规则状态。 |
| G5 长期不活跃清理 | 90 天后具备清理资格，不宣称生产环境自动删除。 | `last_seen_at` 由有效游客会话访问更新。既有 `AccountLifecycle.expireClosed` dry-run/apply 流程纳入此候选；apply 仍受政策和显式删除开关约束。生产计划任务、冷备保留期需运营核验。 |
| G6 重复建游客 | 同一有效 cookie 重复调用创建接口会复用当前游客。每个客户端 IP 在一个固定 1 小时窗口最多新建 3 个游客账号。 | 频控键是 `HMAC-SHA256(AUTH_SECRET, "guest-create\\0" + IP)`，不保存明文 IP。它不是设备指纹：同 NAT 用户共享限额，换 IP 或删除 cookie 不能被当成设备级强约束。生产反向代理必须按部署说明配置可信代理地址。 |

### §4 与数据模型

1. **G1–G6：** 见上表。期限、持久化范围和频控是本次工程决策；90 天清理只证明进入受控流程的资格，不证明生产任务已配置。
2. **A3：选 `email NULL`。** 游客不是邮箱身份。用假邮箱会污染唯一性、登录、导出和通知语义。PostgreSQL 唯一索引允许多个 NULL；新增检查约束强制 `is_guest = (email IS NULL)`，旧邮箱行默认 `is_guest=false`。
3. **G2：游客可用云档。** 云档始终从服务端 session 解析 `ownerId`，忽略请求体中的归属声明；存档编号本身不能读取其他账号数据。D2 必须由两个真实数据库会话验证。
4. **升级证明：** 必须持有当前未过期游客 cookie、提交明确升级确认，并验证目标邮箱 OTP。若邮箱已绑定任何现存账号，返回不区分原因的 `UPGRADE_UNAVAILABLE`；不合并、不接管、不迁移已有账号。

游客 `id` 使用 `randomUUID()`，不使用可预测序号。游客创建不读写 `auth_challenges`。OTP 只在升级邮箱时使用。会话轮换和吊销复用已有认证表及 API。

## §4 四项门槛回答

1. **G1–G6：** 结论、期限、身份保留、云档、清除与频控边界见上方表格。7 天期限、90 天候选清理与 3/IP/小时是本次明确作出的工程策略，单测/集成测试验证对应实现；它们不是来自外部标准或生产运营现状。
2. **A3：** 选 `email NULL`，不是占位邮箱。邮箱代表可验证登录凭据；虚构值会污染唯一性、邮箱登录和生命周期语义。迁移约束校验 `is_guest` 与 NULL 状态一致；PostgreSQL 集成测试读取并验证游客行为。
3. **G2 云同步：** 游客可同步。请求不接受客户端 owner 声明，归属来自当前服务端 session；会话 token 使用随机 32 字节生成，数据库只保存 SHA-256 摘要。D2 集成测试实测游客 A 不能读游客 B 的云档，伪造请求 ownerId 也不能改归属。
4. **升级认证强度：** 不无条件接管。必须同时持有当前游客 session、通过目标邮箱 OTP、提交显式升级确认，且目标邮箱尚未绑定其他账号；碰撞时统一返回 `UPGRADE_UNAVAILABLE`，不合并、不夺取既有账号。D3/D4 集成测试覆盖 owner ID 保持与冲突拒绝。

## 迁移与回滚

新增 `packages/db/drizzle/0018_p1_guest_accounts.sql`；没有改写历史迁移。

```sql
ALTER TABLE auth_accounts ALTER COLUMN email DROP NOT NULL;
ALTER TABLE auth_accounts ADD COLUMN is_guest boolean NOT NULL DEFAULT false;
ALTER TABLE auth_accounts ADD COLUMN last_seen_at timestamptz NOT NULL DEFAULT now();
ALTER TABLE auth_accounts ADD CONSTRAINT auth_accounts_identity_check
  CHECK ((is_guest = (email IS NULL)) IS TRUE);
CREATE INDEX auth_accounts_guest_retention_idx ON auth_accounts(last_seen_at, id)
  WHERE is_guest AND closed_at IS NULL;
```

回滚只能在停用所有新版本 guest API 后进行。先通过获批的数据导出/邮箱升级/账号擦除流程处理所有游客；不得直接删除用户资料，也不得为游客编造邮箱。确认无游客、无 NULL 邮箱行后，在单一事务内执行：

```sql
BEGIN;
DO $$
BEGIN
  IF EXISTS (SELECT 1 FROM auth_accounts WHERE is_guest OR email IS NULL) THEN
    RAISE EXCEPTION 'GUEST_ACCOUNTS_REMAIN';
  END IF;
END $$;
DROP INDEX auth_accounts_guest_retention_idx;
ALTER TABLE auth_accounts DROP CONSTRAINT auth_accounts_identity_check;
ALTER TABLE auth_accounts DROP COLUMN last_seen_at;
ALTER TABLE auth_accounts DROP COLUMN is_guest;
ALTER TABLE auth_accounts ALTER COLUMN email SET NOT NULL;
COMMIT;
```

若守卫失败，事务应回滚并停止；保留迁移和数据，不能用占位邮箱绕过。

## 安全与产品边界

- 游客新建可从角色建档页直接触发，不需邮箱、手机号或已预置 session。邮箱验证码登录仍保留，且其输入、发送、登录、恢复控件在游客入口之前、原文不变。
- 已有邮箱 session 调用游客创建会收到 `ACCOUNT_SESSION_ACTIVE`，不会被降级。重复有效游客 cookie 得到同一 `ownerId`。
- `CloudGame` 和 `/api/games/:saveId` 仍使用服务端 session、规则 runtime 与事务链。不得为移除开发态 wrapper 而暴露本地 review reducer；那会允许浏览器绕过规则事实写入边界。
- 游客模式没有改变 Canon、作者规则门、P1 plugin 或部署 Compose。服务端规则未就绪仍 fail closed。
- 本次没有生产 API URL、真实公网服务器或实际删除调度证据。不能把本地 E2E 写成网站上线、生产 E2E 或真机验收。
