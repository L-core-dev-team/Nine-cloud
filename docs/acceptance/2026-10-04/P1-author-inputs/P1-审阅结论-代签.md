### ① NLU-11：`utterance` 内的否定不压掉 talk —— ✅ 无缺陷

**裁定**：无缺陷。不需修改代码。**建议仅补一条回归测试**（非阻塞）。

**依据**（`packages/domain/src/nlu/action-parser.ts:129-135`）：

```ts
// A direct quote addressed to an NPC is speech content, not an instruction
// to the game. Negation inside that quote must not suppress the talk action.
const containsSpeech = matches.some(match => match.template.kind === 'talk');
if (!containsSpeech && (NEGATION_OR_CONDITION.test(text) || UNRESOLVED_REFERENCE.test(text))) {
```

判定链：玩家输入「对岑九说：不要去望气台」→ `matchTemplate` 先成功匹配 `talk` 模板（`prefix` 命中「对岑九说：」，`utterance` 捕获后半句）→ `containsSpeech === true` → **整个否定/指代拒绝分支被跳过** → 产出 `kind: 'talk'`，`utterance` 保留「不要去望气台」原文。行为与盲标表 NLU-11 期望一致。

**防御深度（额外核验）**：模板自身也受约束。`action-parser.ts:277` 附近对 `template.prefix` 施加同样的否定/指代检查，违规注册会抛 `P1_NLU_TEMPLATE_INVALID`。这意味着**无法通过注册一个「不要去…」模板来绕过拒绝逻辑**。两层防护都在。

**为什么仍建议加回归测试**（残留风险，低）：守卫的正确性依赖「`talk` 模板先成功匹配」。若将来某句同时可匹配 `talk` 与 `move`（例如「对岑九说：去望气台」既像对话又像移动指令），`containsSpeech` 仍为 true，否定检查被跳过——此时行为是「当成对话」，而作者可能期望「澄清」。当前模板集下不存在这种歧义句，**故为潜在风险而非现存缺陷**。

**建议测试用例**（可直接落入 `action-parser.test.ts`）：

| 用例 | 输入 | 期望 |
| --- | --- | --- |
| R-1 | `对岑九说：不要去望气台` | `ready`，`kind='talk'`，`utterance='不要去望气台'` |
| R-2 | `对岑九说：如果天没黑就去` | `ready`，`kind='talk'`，`utterance` 原文保留 |

### ② `combat` 的 `targetId` 可见性来源 —— 裁定：**新增独立目录源 `combatTargets`**

#### 裁定内容

`combat.targetId` **不并入 `npcPresence`**，改为新增第 6 个可见目录源：

```ts
export type VisibleTargetSource =
  | 'knownLocations' | 'npcPresence' | 'observationTargets'
  | 'clues' | 'inventory' | 'combatTargets';   // ← 新增
```

并同步扩展三处封闭类型（缺一不可，否则类型不闭合）：

| 位置 | 现状 | 需改为 |
| --- | --- | --- |
| `action-parser.ts:9` `VisibleTargetSource` | 5 个源 | 追加 `'combatTargets'` |
| `action-parser.ts:38-43` `EntitySlotForKind` | 4 个 kind（封闭联合） | 追加 `combat: { source: 'combatTargets'; slot: 'targetId' }` |
| `action-parser.ts:56-60` `ActionTemplate` | 4 个变体（封闭联合） | 追加 `kind:'combat'; entitySource:'combatTargets'; capture?: never` |
| `action-parser.ts:81-86` `ENTITY_SLOT_POLICY` | 4 行 | 追加 `combat: { ..., combatTargets: 'targetId' }` |

**注意 `BoundActionKind = keyof EntitySlotForKind`**（`:45`）。这不是配置表少了一行的问题——`ENTITY_SLOT_POLICY` 的类型是 `Record<BoundActionKind, ...>`，而 `BoundActionKind` 由封闭联合推导。**不扩 `EntitySlotForKind`，`ENTITY_SLOT_POLICY` 连加一行的资格都没有。** 这也是为什么 PR #51 未支持 `combat` 属于类型层面的有意边界，而非疏漏。

#### 为什么**不**并入 `npcPresence`（这是本裁定的实质）

理由是**避免错误的可供性（affordance）**，不是代码风格问题。

序章里的战斗目标是**灰羽鸦**（`packages/content/src/prologue/prologue-v1.ts:201`）：

```ts
{ kind: 'combat', description: '驱退灰羽鸦。' },
```

鸦不是人。若把 `combat.targetId` 塞进 `npcPresence`：

1. `talk` 的实体源也是 `npcPresence`（`action-parser.ts:41`），因此**鸦会同时出现在「可对话对象」列表里**；
2. 玩家选中鸦发起对话，规则层 `resolveTalk`（`prologue-v1-rules.ts:416-417`）执行 `book.npcs.find(...)` 必然落空 → 返回 `INPUT_NO_SUCH_TARGET`；
3. 于是产生一个**玩家可见的自相矛盾**：界面先承诺「可以跟它说话」，点下去报「没有这个目标」。

这类缺陷不会崩服务、不会脏数据，但会直接损伤「真实感」与「沉浸体验感」——正是本项目的核心品质目标。**两个语义不同的目录，不能合并。**

#### 双层防护：规则层已有 fail-closed 校验

裁定不新增授权逻辑，因为**规则层已经写好了**（`packages/domain/src/prologue-v1-rules.ts:502-505`）：

```ts
const target = book.combatTargets.find(candidate => candidate.targetId === action.payload.targetId);
if (!target) return reject('INPUT_NO_SUCH_TARGET');
if (target.locationId !== state.locationId) return reject('AUTH_UNAUTHORIZED_TARGET');
```

即：**解析器层**用目录做词面授权（防止玩家输入不存在或不存在的场景内的目标），**规则层**再做一次权威校验（防止绕过解析器直接构造 intent）。两层同向，fail-closed。

这与 `talk` 的处理完全同构（`prologue-v1-rules.ts:416-418` 的 `AUTH_NPC_ABSENT`）。因此裁定②与现有架构一致，不引入新范式。

### ③ `npcPresence` 的权威来源 —— 裁定：**派生投影，不写入状态**

#### 裁定内容

`npcPresence` **不进 `WorldState`，也不进 `PrologueV1Facts`**。它是一个**在装配层即时派生的可见目录**，来源为：

```
npcPresence = book.npcs
  .filter(npc => npc.locationId === save.state.locationId)
  .map(npc => ({ id: npc.npcId, label: <来自内容包 entry('npc_cenjiu').content.name>, aliases: <口语别名> }))
```

同一份派生逻辑同时产出 `combatTargets`、`observationTargets`、`knownLocations`、`inventory`、`clues` 五个目录，**六目录同 revision 一次性成型，作为整体交给 `parseActionText`**。

#### 为什么不能写进 `WorldStateSchema`（三条硬理由）

1. **契约封闭性**。`WorldStateSchema` 是 `z.strictObject`（`packages/contracts/src/world.ts:4-10`），只有 `playerId` / `locationId` / `elapsedMinutes` / `facts` 四字段。加字段会改变存档形状，而 `SaveEnvelopeV1Schema`（`save.ts:26-34`）必须保持可读——**P1 的第一条不变量就是 legacy 存档不被破坏**。`PrologueV1FactsSchema`（`prologue.ts:44-78`）同样是 `strictObject`，其源码注释已明确设计意图：

   > `Closed P1 prologue facts. This is intentionally separate from WorldStateSchema: legacy saves remain readable, while the signed prologue rules reject unknown projection fields instead of treating facts as an extension bag.`

   `facts` 是**封闭的事实包，不是扩展袋**。在场信息不属于「事实」，它由「规则簿 + 当前位置」**决定**，存下来只会引入可漂移的冗余副本。

2. **漂移风险**。若持久化，`locationId` 变更与 `npcPresence` 变更必须原子一致。`applyStateDelta`（`state-delta.ts:3-12`）只处理 `locationChange` 与 `factChanges`，**没有第三种变更类型**。新增一类 delta 会扩大状态机面，而收益为零——因为在场集合完全可以**算**出来，不必**存**下来。

3. **revision 绑定**。解析器有硬守卫（`action-parser.ts:112-114`）：

   ```ts
   if (input.visibilityRevision !== input.identity.expectedRevision) {
     return clarify('unknown', input.identity, '刚才看到的行动信息已过时。请刷新后重新选择。', [], []);
   }
   ```

   可见目录必须与 `expectedRevision` 严格同 revision。**即时派生天然满足**（读的就是当前 state）；持久化则必须额外证明「存档里的 presence 属于当前 revision」，反而增加一个可失效环节。

#### 第二重锚点：可见性策略已被存档钉住

`SaveMemoryPolicySchema`（`save.ts:11-23`）已包含：

```ts
visibilityPolicyVersion: z.string().min(1).max(200),
visibilityPolicyHash: sha256ArtifactHash,
```

可见性策略是**存档创建时钉死的、不可变的、带哈希的身份**。因此派生实现必须满足：

- 目录产出逻辑的版本号 ≡ `save.memoryPolicy.visibilityPolicyVersion`
- 该逻辑制品的 `sha256` ≡ `save.memoryPolicy.visibilityPolicyHash`
- **hash 不匹配 ⇒ fail-closed，目录置空**，不得回退到「显示全部」

最后一条是关键安全边界：目录为空时，`talk` 匹配不到任何人 → 产出 `clarify` → 0 事件。**宁可不给选项，不可给错选项。**

#### 派生失败时的 fail-closed 矩阵

| 情形 | 行为 |
| --- | --- |
| `book.npcs` 缺失 / 为空 | `npcPresence = []`，不报错 |
| `locationId` 在 `book.locationIds` 中不存在 | `npcPresence = []`，不报错 |
| `visibilityPolicyHash` 不匹配 | **全部六目录置空** |
| `npc.locationId` 不等于当前 `locationId` | 该 NPC 不出现在目录中 |

均**不抛异常、不阻断回合**。理由：可见性是「展示层授权」，不是「状态一致性」。把展示层问题升级为回合失败，会让一次配置漂移变成玩家无法游玩。
