# 《九霄》合作者执行方案

> 角色：项目发起者、产品主理人、世界观与 Canon 负责人
>
> 目的：把思想优势转成可实现、可审查、可验收的产品输入。

## 1. 你的最终责任

你负责回答四个问题：

1. 《九霄》为什么值得存在？
2. 玩家每十分钟应获得什么体验？
3. 什么内容属于原设，什么内容允许系统生成？
4. 一次实现何时算“仍然是九霄”？

你不负责决定代码框架，但你有权拒绝背离宗旨的实现。拒绝必须对应具体场景、原设或体验证据。

## 2. 你每个 Sprint 的固定产物

- 一个最多两页的功能规格；
- 3—10 个玩家故事；
- 允许、禁止和待确认示例；
- Canon 来源或“待核”标记；
- 可操作的验收脚本；
- 对上一 Sprint 的产品结论。

不得只交付“感觉更真实”“更像开放世界”之类的描述。

## 3. 当前四周任务

### 第 1 周：产品宪章

完成：

- 一句话产品定义；
- 三条不可牺牲原则；
- 0 号试玩范围；
- 明确非目标；
- 目标玩家和典型游玩时长；
- 经典记忆与拟真记忆的体验差异；
- 小说模式与图片剧情模式的优先顺序。

验收：陌生开发者读完后，能判断一个需求是否属于 0 号试玩。

### 第 2 周：关键 Canon

从 182 张 OCR 中只先核对直接影响试玩的条目：

- 境界顺序与突破边界；
- 五域、开局地点和宗门；
- 基础物品、货币和所有权；
- 死亡、伤势与复活边界；
- 关键人物的身份、关系和认知边界。

每条保留来源。无法确认时写“待核”，不能让模型补齐。

### 第 3 周：十个试玩场景

至少覆盖：

- 普通对话；
- 修炼；
- 战斗；
- 使用与消耗物品；
- 获得任务；
- 地图移动；
- 角色死亡；
- 秘密与欺骗；
- 多年后重逢；
- 失败恢复。

每个场景写输入、前置状态、允许结果、禁止结果和体验判断。

### 第 4 周：地图与记忆体验

- 画出第一版节点地图；
- 为每条边写时间、条件和可见性；
- 选 5 个“应该永远记住”的事件；
- 选 5 个“可以逐渐模糊”的事件；
- 选 5 个“容易因干扰记错”的事件；
- 为三个 NPC 写不同的信息来源与回忆表现。

## 4. 七阶段中的主责任务

| 阶段 | 你的主交付 |
| --- | --- |
| 一 | 产品宪章、核心循环、关键 Canon、试玩验收 |
| 二 | 玩家行动语料、歧义与期望意图 |
| 三 | 领域规则语义、战力边界、结果合理性 |
| 四 | 记忆重要性、遗忘体验、世界历史叙事 |
| 五 | NPC 知识边界、人格、秘密与传播规则 |
| 六 | 宗门/势力演化、大事件边界、开放世界体验 |
| 七 | 九霄内容包与第二题材的体验差异 |

## 5. GitHub 操作

每项需求先建 Issue。分支使用 `product/<topic>`。PR 中必须填写：

- 变更的产品问题；
- Canon 来源；
- 新增与拒绝的行为；
- 验收步骤；
- 对旧存档或旧设定的影响。

你对技术 PR 的审查重点：人物是否 OOC、结果是否像九霄、是否限制自由、是否误改原设。不要用代码风格代替产品审查。

## 6. 你必须避免的失误

- 不要在聊天中不断扩大范围而不更新 Issue；
- 不要把模型写得流畅当作规则正确；
- 不要把 OCR 草稿当 Canon；
- 不要同时要求开放世界、多端上架、图片剧情和平台化；
- 不要用“更真实”掩盖不可验收的要求；
- 不要在技术实现后才第一次说明核心体验。

## 8. 你的完成定义

一个产品任务只有在以下条件同时满足时完成：

- 有来源或明确标注为本局生成；
- 有至少一个正常案例和一个反例；
- 能由试玩步骤复现；
- 已说明与原设、旧档和未来阶段的关系；
- 你已经亲自运行并给出明确结论。
