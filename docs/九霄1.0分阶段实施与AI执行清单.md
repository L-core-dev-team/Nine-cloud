## 0. AI 执行纪律

1. 从 GitHub 当前 `main` 拉取并建 `codex/` 功能分支；先运行 `git status`。不要在本地旧 `codex/ui-v1-redesign` 直接追加。保留 `.workbuddy/` 等用户未跟踪目录，不清理未知文件。
2. 每阶段先读相关旧文件、现有测试和本文件，再给出短实施清单。只实现本阶段；发现契约需变化，先写 ADR 并更新依赖阶段，不悄悄扩大范围。
3. 世界资料遵循原图→OCR→作者裁定→发布 Canon。现有 `outputs/设定OCR数据.json` 的 182 项仍待逐图核对；没有原图不得将其作为已审内容发布。AI 不代替作者裁定人物或设定冲突。
4. 任何叙事模型、NPC 记忆、生成媒体、插件与 MCP 只能读取经权限过滤的状态或提出行动候选；只有规则事务可提交 `DomainEvent`。禁止把模型输出直接写入境界、位置、物品、任务或账本。
5. 每个 PR 写明改动文件、旧能力影响、测试实际运行结果、失败结果、截图/日志位置、回退方式和需要作者 A/B 裁决的问题。`MERGEABLE` 不等于已合并，单测通过不等于产品验收。
6. 不在代码、文档、日志、测试夹具或 PR 中放真实密钥、私人原图、未脱敏存档。对需要商户和真实模型的测试使用隔离环境；没有外部账号时诚实记录“未实测”。

## 2. 贯穿各阶段的最小契约

S1 先定义并锁定运行校验。`packages/contracts/src/action.ts` 描述 `ActionIntent`：`saveId`、`actorId`、`kind`、`payload`、`expectedRevision`、`idempotencyKey`；`decision.ts` 描述通过、失败和需澄清三种结果；`event.ts` 描述事件 ID、类型、前后版本、时间、来源和可回放负载；`save.ts` 描述 `SaveEnvelope` 的 `schemaVersion`、`canonVersion`、`ruleVersion`、`memoryPolicyVersion`、`revision` 与状态快照。字段的具体联合类型从旧档和已签规则表导出，不能为了迁移方便任意丢字段。

事务顺序固定：校验存档归属与版本 → 解析意图 → 规则决定 → 在同一事务写事件和新修订 → 提交后异步叙事。重复 `idempotencyKey` 返回第一次的事件及结果，不再次消耗物品、额度或世界时间。叙事失败在 `story_renders` 记失败并可重试，不回滚已提交事件。游客局在本地实现相同纯规则；云档在 API 执行规则。两者用同一组合同测试。

接口路径按资源固定为 `/api/saves`、`/api/saves/:id/turns`、`/api/media-jobs`、`/api/shares`、`/api/entitlements`、`/api/usage`、`/api/billing/*`，认证挂在 `/api/auth/*`。所有私有资源先做对象级授权；请求携带版本，响应带可操作错误码，不把数据库或服务商原始错误直接显示给玩家。实现者可以在 ADR 中细化 HTTP 方法和分页，但不能改变上述权威顺序与权限边界。
