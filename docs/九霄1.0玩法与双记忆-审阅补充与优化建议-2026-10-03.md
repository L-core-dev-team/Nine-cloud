## 2. 新增证据（2026-10-03 联网核实）

### 2.1 学术根基被漏引：Generative Agents

`FACT` 原方案引用了 ACT-R、Oblivion、Memora、PersonaForge，**但未引用 NPC 记忆检索的奠基工作**：

> Park, Joon Sung, et al. "Generative Agents: Interactive Simulacra of Human Behavior." *UIST 2023*, arXiv:2304.03442.

其检索式为三项**线性加和**（论文中 α 全为 1）：

```
score = α_recency·recency + α_importance·importance + α_relevance·relevance
  recency    = γ^(距上次访问小时数)，实现中 γ = 0.995
  importance = LLM 打分 1–10 的 poignancy（刷牙=2，失恋/录取=8~10）
  relevance  = 查询与记忆 embedding 的余弦相似度
```

**必须在方案中显式回应的四点分岔：**

| | Generative Agents | 《九霄》 | 建议 |
| --- | --- | --- | --- |
| 分数语义 | **排序**（召回哪几条） | **门控**（`minAccessibility` 能不能召回） | 九霄更严格，**声明这是刻意偏离** |
| 形状 | 三项加和 | `S × 2^(-…)` 乘性衰减 | 保留九霄形式，补「为何不用加和式」 |
| 重要度来源 | **LLM 打分**（不可复现） | 规则/作者给定（可复现） | **九霄更优**，把 GA 作为「为何不这样做」的对照写入 |
| 线索 | 连续余弦相似度 | 类型化线索 C | 九霄更可审计 |

### 2.2 记忆失效的真正瓶颈不是「召回」，是「取代」

| 来源 | 结论 |
| --- | --- |
| STALE（arXiv 2605.06527） | 致命失败是**隐式冲突**：后续观察使早期记忆失效但无显式否定。三维度：**State Resolution**、**Premise Resistance**、**Implicit Policy Adaptation**。最佳前沿模型仅 **55.2%**。 |
| Supersede（arXiv 2606.27472） | 有界自维护记忆替换全上下文，准确率 **92% → 77%**；**对话增长 24 倍时 68% → 28%**，给更多记忆**无恢复（28%→28%）**。瓶颈在**记忆维护/写修订路径**。 |
| Memora / FAMA（ACL 2026 Findings, pp. 26814–26841, DOI `10.18653/v1/2026.findings-acl.1337`） | FAMA 惩罚依赖已过时记忆。记忆操作分布 Add 68% / **Update 13%** / Delete 19%——**更新只占 13%，却是失败主因**。 |

> STALE/Supersede 为二手转述，**原文需核**【待核】。Memora 的 ACL Anthology 页为一手出处；**该正式出处可替换原方案中的 arXiv 预印本引用**。

### 2.3 记忆框架横向基线（LongMemEval-S，二手，仅供对照）

| 方案 | 分数 |
| --- | --- |
| 全上下文 GPT-4o（115K） | 62.1% |
| **Mem0 v1（独立复测）** | **49.0%（低于全上下文）** |
| Zep / Graphiti（时序知识图） | 63.8%–71.2% |
| Oracle ceiling | 82.4% |
| 2026 前沿（Mastra OM / OMEGA / EverMemOS / TiMem） | 76.9%–95.4%（多为厂商自报） |

> 关键启示：**平面向量检索在时序推理上可能不如不用**——直接支持原方案「外部语义索引只返回候选 ID、最终结果由确定性内核决定」的立场。**不可作为九霄验收数据。**

### 2.4 中文意图解析的可靠性（**风险最高的一块**）

`【待核】` 以下为二手来源，但方向高度一致：

| 场景 | 观察到的准确率 |
| --- | --- |
| 通用领域词义消歧 | ~92.3% |
| **垂直行业术语消歧** | **骤降至 ~76.5%** |
| 基础层（日常口语、指代、意图） | ~96% |
| 逻辑层（嵌套条件、否定、转折） | ~82% |
| **模糊层（多义词、省略主语、方言）** | **~71%** |
| 顶级模型在 20 条歧义句上的误判率 | ~43%（时间悖论类 92%） |

> **对九霄的直接含义**：修仙题材天然多义——「青岚镇」「长老」「师尊」「清心诀」。**模糊层是最低的一档，也正是误解析最危险的一档。**

### 2.5 确定性重放的工程要求（新增）

`【推断 + 二手】` 业界对「确定性重放」的要求高度一致：

| 要素 | 要求 |
| --- | --- |
| 初始种子 | 固定 PRNG 种子，使随机流可复现 |
| **全量决策输入** | **仅记种子不够**：还须记模型快照、prompt 哈希、检索结果与顺序、工具输出、时钟、locale、应用 commit。业界原话：**「The prompt is not the run」** |
| 有序事件日志 | 外部刺激、用户交互、人工覆盖都必须按序落盘 |
| 状态快照 | 定期持久化完整状态向量，支持从任意检查点热启动重放 |
| 单线程/全序 | 关闭并行离散事件仿真（PDES）优化，改用全局时间戳 + 平局优先级 |
| 外部依赖 mock | 外部 API 必须从录制缓存返回，否则一年后重放会因外部数据格式变化而分叉 |
| 逐位比对 | 校验和/哈希比对，任何偏差都暴露非确定性路径（未初始化内存、墙上时钟、无序哈希迭代） |
| 种子面板 | 一个 canonical seed 用于调试，另设一组 seed 做鲁棒性；**只在单个 seed 上通过的修复不算修复** |

> **对九霄的直接含义**：原方案 §4.5 要求「相同签名必得同一结果」，这在**纯函数检索**上成立；但**规则结算一旦含随机，回执（G-15）就不足以证明可复现**。这也是 `event-log.ts` 已经做到一半的地方（`canonicalJson` + SHA-256 指纹）需要补齐「随机与时钟」的原因。

## 4. 问题与建议

### 4.1 【P0·阻断级】缺少「授权观察取代（supersession）」语义

**问题。** 方案定义「授权观察永不删除」与「按衰减分数检索」，但**未定义后续规则事件改变某条观察前提后，检索如何处理**。

> T10 玩家当众羞辱 NPC，T50 双方和解。T10 的观察按方案**不删**。若 T60 检索把它当有效事实返回，即制造新矛盾——这是 §9 明令禁止的「误记/错配」在**时间维度上的变体**。

**建议（不删数据，改在检索时做前提校验）：**

```ts
// packages/contracts/src/memory.ts —— 建议新增
export const SupersessionKindSchema = z.enum([
  'premise-revised', 'relation-changed', 'entity-dead', 'item-moved', 'clue-invalid',
]);

export const SupersessionSchema = z.strictObject({
  saveId: z.string().min(1),
  branchId: z.string().min(1),
  observationGrantId: z.uuid(),
  supersededByEventId: z.uuid(),
  kind: SupersessionKindSchema,
  reason: z.string().min(1),        // 规则产出的可读说明
  policyVersion: z.string().min(1),
});
```

- 新表 `observation_supersessions`，唯一键 `(saveId, branchId, observationGrantId, supersededByEventId)`。
- **由规则事务在写入新 `DomainEvent` 时一并判定并落库**——不新增删除路径，旧观察完整可查。
- `Recall` 扩为 `{observation, accessibility, anchorKind?, supersession?, ambiguousWith?}`。
- **叙事装配规则**：被取代观察**不得**进入 `NarrativeContext` 的**当前状态**槽位；仅在玩家明确追问往事时作为**历史**注入并附 `supersededBy`。

**配套对抗性评测：**

| 评测 | 构造 | 通过标准 |
| --- | --- | --- |
| **Premise Resistance** | 问一个**预设陈旧状态**的问题 | 返回该观察时**必须携带 `supersededBy`**；不得以肯定语气当作当前事实 |
| **State Resolution** | 问"他现在怎么看我"，关系已变更 | 不得引用被取代的关系类观察作为**当前**状态 |
| **Implicit Policy Adaptation** | 关键 NPC 后续对话是否体现新关系 | 被取代观察不进当前状态槽位 |

### 4.2 【P0】线索词典版本与「可复现」承诺冲突

**问题。** 方案把 `线索词典哈希` 放进检索签名并承诺「相同签名必得相同结果」，同时要求 `policyArtifactHash` 写入存档。但词典**持续扩充** → 制品哈希变化 → 旧档签名变化 → **可复现性被破坏**。结合 G-5，该问题**当前已存在**。

**建议（三选一，须写入方案 §4.2 字段表）：**

1. **存档锁定制品（推荐）**：建档时固化 `policyArtifactHash`（含词典快照）。词典升级只对新档生效；旧档升级走**分支迁移**——复用既有 branch lineage 机制。
2. **词典只增不改**：词典项加 `effectiveFromPolicy`，检索按存档锁定版本过滤。
3. **词典独立出版本化**：与 policy 解耦。复杂度最高。

### 4.3 【P0】缺少「误解析率」指标，且多义专名与 `observe` 无处安放

**问题。** §7 有「行动空转 < 5%」，衡量的是**浪费**；没衡量**误解析**（把玩家意图解析成另一个动作并结算）。叠加两处契约缺口：G-11（无 `observe`）、G-12（`clarify` 无候选）。

**建议：** 指标表补三行，误解析列为**阻断级**：

| 指标 | 口径 | 目标 |
| --- | --- | --- |
| **误解析率** | 被规则层接纳但与玩家真实意图不符的回合 ÷ 被接纳回合。**双人盲标** | **0** |
| **多义专名消歧** | 修仙高歧义词正确消歧或显式澄清 | 100% |
| **过度澄清率** | 本可直接执行却要求澄清的比例 | 设上限并逐版本下降 |

**配套交付物**（把原方案 P0-6 升格为带门槛的工程件）：正样本、负样本（否定/条件/疑问/多义指代/数量词/方位词/跨回合指代）、多义专名表；门槛为负样本 ≥ N、专名 ≥ M、盲标误解析率 = 0。

### 4.4 【P1】衰减公式：三处需要收敛

**问题。** 方案 P5 基线为 `A = clamp(S × 2^(-(Δg/Hg + Δn/Hn)) + C, 0, 1)`，实现是 `1/(1 + elapsed/1440)`（G-6），二者关系与切换条件**未定义**。

**建议：**

```
A_decay = S × 2^-( λ·Δg/Hg + (1-λ)·Δn/Hn )     λ ∈ [0,1] 为显式权重
A_final = A_decay × (1 + C)                        C ∈ [0,1]，线索修正改乘性
门控：minAccessibility 仍是硬门槛（保留方案原语义，优于 GA 的纯排序）
特例：anchorKind = 'fact-anchor' 的片段不受门控约束
```

三个收益：① **λ 成为唯一需盲评调参的标量**；② **C 改乘性后线索无法「解锁」完全衰减的片段**；③ **保留门控语义**——这是九霄优于 GA 之处，应显式记录理由。方案的**单调性要求完全保留**。

### 4.5 【P1】锚点与衰减的关系未定义

**建议明确三条：**

- **事实字段锚点**（姓名、关系等级、是否已结识、关键承诺）**不受衰减**，存结构化字段，标 `anchorKind: 'fact-anchor'`。
- **情节回忆**（具体场景、原话、情绪）**受衰减与线索约束**。
- 锚点**只回答「现在是什么关系」**，不得作为情节片段的替代，也不得携带情节细节。

建议在 §4.1「三种数据不能混称记忆」表中补第四行「结构化关系锚点」。

### 4.6 【P1】缺少「上下文装配预算表」

| 优先级 | 内容 | 建议预算 | 裁剪规则 |
| --- | --- | --- | --- |
| P0 必放 | 身份锚点 + 关系锚点 + 当前结构化状态 | ~15% | **不裁剪** |
| P0 必放 | 本轮 `TurnReceipt` 与允许表达的事实 | ~10% | **不裁剪** |
| P1 | 场景/环境事实 | ~10% | 按状态相关性 |
| P1 | 线索召回的授权片段（**含 `supersededBy`**） | ~30% | 按分数降序，**不得跨模式取** |
| P2 | 最近 K 回合叙事正文 | ~25% | K 固定，不随上下文增长 |
| P3 | 长线摘要 PlotDigest | ~10% | 仅在需要跨回合推理时注入 |

**「不裁剪区」必须显式存在**，否则长局中最先被挤掉的是身份与关系——正是 T5–T80 依赖的部分。

### 4.7 【P1】规则层缺少显式评估上下文（G-13）

**影响范围澄清**：服务端不受限——`rule-resolver.ts` / `server-turn.ts` 已把规则与可见性做成**宿主注入的版本化实现**。**受影响的是游客/本地零配置路径**，而那正是 P3 的核心。

**建议：**

```ts
type RuleContext = {
  nowMinute: number;            // 来自世界时钟，非 Date.now()
  rulesVersion: string;         // 与 DomainEvent.ruleVersion 一致
  visibility: (npcId: string) => readonly string[];  // 可见性纯函数
  random: () => number;         // 由 rngSeed 播种的确定性源
  rngSeed: string;
};

evaluate(intent, save, ctx)         // packages/domain/src/rules.ts
decide(intent, save, ctx)           // prepareTurn 的回调签名
```

并按 §4.9 要求把 `rngSeed` 与实际抽值写入 `TurnReceipt`。

### 4.8 【P1】`free_text` 必须有显式处置规则

`FACT` `ActionIntentSchema` 含第 8 个 kind `free_text{text}`，但方案**没有规定规则层如何处置它**。

**风险**：若某条规则把 `free_text` 当作可执行行动（例如「我要走」被当作移动），就绕过了整个确定性解析器。

**建议**：在规则表中**显式写死**：`free_text` 一律不接受、不结算、不推进时间，返回 `clarify`（附原文引用与可接受动作示例）或 `rejected(code='UNPARSED')`。列为规则表必填项。

### 4.9 【P1·新增】回执必须承载随机、时钟与规则版本（G-15/G-20）

**问题。** `TurnReceipt` 现有 5 个字段，`requestFingerprint` 只覆盖 intent。方案 §9 要求「所有随机只在规则事件中有种子、版本和回执」——**当前回执结构无处承载**。结合 §2.5 的确定性重放要求（仅记种子不够，须记全量决策输入），建议：

```ts
export const TurnReceiptSchema = z.strictObject({
  // 保留既有
  idempotencyKey: z.uuid(),
  saveId: z.string().min(1),
  requestFingerprint: z.string().min(1),
  decision: DecisionSchema,
  resultingRevision: z.int().nonnegative(),
  // 新增
  branchId: z.string().min(1),
  rulesVersion: z.string().min(1),
  memoryPolicyArtifactHash: z.string().min(1),
  clockMinute: z.int().nonnegative(),      // 来自世界时钟，不是墙上时钟
  rng: z.strictObject({
    seed: z.string().min(1),
    draws: z.array(z.number()).max(64),   // 实际抽值，顺序固定
  }),
  appCommit: z.string().min(1),           // 便于按同一 commit 重放
});
```

**要点**：
- `rng.draws` 记录**实际抽值**而非仅种子——因为 PRNG 版本或调用次数变化会改变流，记录抽值才能跨版本重放。
- `clockMinute` 必须是**世界时钟**，不得是 `Date.now()`。
- `memoryPolicyArtifactHash` 让「同一存档 + 同一策略」的重放可验证（呼应 §4.2）。
- 这一条同时解决 G-20（请求指纹 ≠ 决策指纹）。

### 4.10 【P1·新增】`clarify` 后的重试语义必须裁定（G-16）

**问题。** `prepareTurn` 的行为链：

```
prior.idempotencyKey === intent.idempotencyKey
  ├─ prior.saveId / requestFingerprint 相同 → duplicate        （正确）
  └─ requestFingerprint 不同              → idempotency-conflict （阻断合法重试）
```

而 `rejected` 与 `clarify` **同样会产生 `recorded` 回执**（`event-log.ts:125-131`）。因此：

> 玩家收到「缺少目标」→ 补充参数 → 用**同一个** `idempotencyKey` 重新提交 → `requestFingerprint` 不同 → **`idempotency-conflict`，合法重试被拒。**

**这使原方案 P3-4「歧义时列出候选让玩家选」的交互在契约层走不通。** 方案 P3-1 只说「缺参数/歧义只返回 clarification，不触发 DomainEvent」，**未定义 clarify 之后算不算同一回合**。

**建议二选一，交 A/B 裁定：**

| 选项 | 做法 | 影响 |
| --- | --- | --- |
| **A（同回合语义）** | 域层对 `decision.status !== 'accepted'` 的 prior receipt **不返回 duplicate/conflict**，允许同 key 重试；仅 `accepted` 才锁幂等 | 语义直观，但需明确「同 key 不同输入」在非 accepted 情形下不算冲突 |
| **B（换 key 语义）** | 契约显式规定：`clarify` 后客户端**必须**生成新 `idempotencyKey`；域层行为不变 | 改动小，但每个前端实现者都会踩坑，须写入契约注释与 P3 验收 |

> 【推断】倾向 **A**：`clarify` 在语义上是「这一回合尚未完成」，把它与「已完成回合的幂等重放」区分开更符合方案原文「澄清和规则拒绝属于尚未完成的输入，不计为成功回合」。

### 4.11 【P1·新增】「观察」的建模必须裁决（G-11）

方案 §3.2 要求序章五类含「观察」，且「观察必须产生规则定义的观察/调查记录或可验证线索变化，不允许只回一段空泛描写」。但契约无 `observe`。

| 选项 | 做法 | 评价 |
| --- | --- | --- |
| **A 新增 kind** | `observe{targetId, method?}` | **推荐**。语义与 `talk`（产生对话/关系）不同，且能直接承载线索事件 |
| B 并入 `talk` | `talk{npcId, utterance}` 兼任观察 | 会让「交谈是否产生好感」的规则污染观察语义 |
| C 并入 `free_text` | 由规则解析 | **不可行**，正是 §4.8 要防的绕过路径 |

### 4.12 【P2】其余五项

| 项 | 建议 |
| --- | --- |
| **规则版本迁移**（G-17） | 事件 `ruleVersion` 严格等于 `save.ruleVersion` ⇒ 规则升级后旧档无法接受新事件。**必须与 `branchId` 同批设计**：新规则版本只在新分支生效，旧分支保持旧规则；两者都用 SP-0 的迁移登记 |
| **`belief.ts` 正名**（G-18） | 文件名承诺了信念模型但未实现。建议改名为 `observation-writer.ts`，或补最小 `Belief{veter npcId, proposition, confidence, sourceGrantId}`——原方案 §8 第 3 项「表里人格/认知可见性」在代码里尚无落点 |
| **统一 canonical JSON**（G-18/G-19） | 导出 `event-log.ts` 的 `canonicalJson`，`belief.ts:35` 的 `JSON.stringify` 比较改用它；记忆制品摘要、词典摘要、fixture 指纹全部复用同一实现与同一版本号 |
| **双模式惰性投影** | outbox 保持 mode 中立，但**只投影到当前选中的模式库**；另一库仅在创建跨模式分支时一次性重建 |
| **移动端后台冻结** | 长回合考虑 `navigator.wakeLock`；或事务提交后立即持久化「已提交待叙事」标记，使恢复不依赖页面存活 |

### 4.13 【P2·新增】把「回执是唯一事实凭证」落成分层断言

原方案 §9 要求「不得宣称模型散文已被完整验证」。建议落成**可执行的断言层级**（顺序不可颠倒）：

| 层 | 断言 | 通过标准 |
| --- | --- | --- |
| L1 | schema 校验 | 正文与槽位符合契约 |
| L2 | **事实回指** | 姓名/关系/物品/位置/历史断言必须能回指 receipt、当前投影、批准 Canon 或授权观察 |
| L3 | **禁用动作** | 未授权 `eventId` 出现在 `MemoryEvidence` / `NarrativeContext` 即失败（硬门禁） |
| L4 | 引用支持 | 每条断言附 `factId`/`eventId` |
| L5 | 任务结果 | 首个任务在无模型路径完成 |
| L6 | 可选 model grader | **grader 的 prompt 与 seed 也必须固定并记录**，否则会把稳定答案判成 flaky |

> 原则：**L1–L4 是确定性断言，不依赖模型；只有 L6 允许不确定性。** 顺序颠倒就会出现「用模型证明模型没编」。

## 5. 逐阶段可执行补充步骤（SP-0 … SP-7）

> 映射关系：SP-n 是对原方案 P-n 的**补充动作**，不替代原阶段。每一项须由 A/B 签收后才执行。

### SP-0 · 契约冻结与差距登记（对应 P0）

**前置**：先裁决 §4.2（词典策略）、§4.5（锚点定义）、§4.11（观察建模）——G-1/G-2/G-11 的字段设计依赖它们。

| 步 | 动作 | 文件 | 产出 |
| --- | --- | --- | --- |

| SP-0-2 | 升 schema：`SAVE_SCHEMA_VERSION` 1 → 2 | `contracts/src/save.ts` | 新增 `branchId`、`memoryMode: z.enum(['continue','forgetting'])`、`memoryPolicy: {policyVersion, schemaVersion, clockBasis, policyArtifactHash, lexiconVersion}` |

## 7. 建议的最小可玩切片（风险对冲，非替代）

**问题。** P0–P8 全部未启动，而上游 S3 六类规则仍未签署（`RULES_NOT_READY`，`domain/src/rules.ts` 目前无条件拒绝全部行动）。原计划第一步依赖一个**尚不存在的规则表**，存在长期空转风险。

**建议：** 准备一个**明确标注「工程验证用、不可用于发布」**的最小规则集（一个地点、两个 NPC、一件物品、一个任务目标），要求：

- 仅在 `test` / 隔离环境生效，构建目标带与 `LICENSE_PENDING` 同级的门禁；
- 任何 UI、日志、导出中不得呈现为可玩内容；
- 用途仅限：验证解析器、授权投影、检索纯函数性、**取代判定**、回执链路；
- 保留原方案 §9 红线：不得用合成规则冒充可玩内容。

> 【推断】这能让 P2/P4 的工程验证不必等待 P1 的作者签署，把「工程空转」与「内容待签」两条风险线解耦。**但必须由 A 明确授权为工程夹具**，否则会触碰方案已划过的红线。
